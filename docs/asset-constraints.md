## 摘要：三個最要緊的結論

1. **Canvas 已經是 DPR-aware 的，但上限鎖在 2.5×。**【讀碼】【實測】
   導入貼圖不會因為缺少縮放處理而糊掉。但 3× 裝置實際只會用到 2.5×，所以「@3x 素材」是浪費。
   實測每格 tile 的裝置像素落在 **54–92px**，理論上限 115px。

2. **可讀性目前是靠深色描邊撐住的，不是靠地形夠暗。**【實測】
   資訊層對現有最亮地形色的對比只有 1.0–1.9:1（全部低於 3:1）。
   有描邊／底襯的元素沒事，**沒有描邊的元素**（目標框、雷射線、路徑點、單位本體、屍體、噪音環）
   會在地形一變亮就直接消失。這是導入美術最可能翻車的地方，優先度高於畫質。

3. **GitHub Pages 對帶 hash 的資產也只給 `max-age=600`。**【實測】
   內容雜湊檔名在這裡**拿不到長效快取**，重複造訪 10 分鐘後就要重新驗證。
   這是本專案唯一真正需要 service worker 的理由。

## 1. 目標裝置與解析度

### 1.1 現有 canvas 是 DPR-aware 的【讀碼】

`src/ui/game.ts` 的 `observeResize()`：

```ts
const dpr = Math.min(window.devicePixelRatio || 1, 2.5);
this.canvas.width  = Math.floor(this.viewW * dpr);
this.canvas.height = Math.floor(this.viewH * dpr);
this.ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
```

backing store 依 DPR 放大，繪圖座標維持 CSS 像素。**導入貼圖不需要先補這一層。**

唯一要注意的是那個 `2.5` 上限：它是為了壓記憶體而設的，代價是 3× 裝置只會用到 2.5×。

### 1.2 實測：六種手機直向設定【實測】

| 裝置 | CSS 視窗 | DPR | canvas backing | 實際倍率 | tile (CSS) | tile (裝置px) | 可見格數 |
|---|---|---|---|---|---|---|---|
| iPhone SE 類 | 320×568 | 2 | 640×1136 | ×2.00 | 27 | **54** | 11.9 × 21.0 |
| iPhone 12–14 | 390×844 | 3 | 975×2110 | ×2.50 | 33 | **83** | 11.8 × 25.6 |
| iPhone 14 Pro Max | 430×932 | 3 | 1075×2330 | ×2.50 | 36 | **90** | 11.9 × 25.9 |
| Android 中階 | 360×800 | 3 | 900×2000 | ×2.50 | 30 | **75** | 12.0 × 26.7 |
| Android 大螢幕 | 412×915 | 2.625 | 1030×2287 | ×2.50 | 34 | **85** | 12.1 × 26.9 |
| 小型平板直向 | 768×1024 | 2 | 1536×2048 | ×2.00 | 46 | **92** | 16.7 × 22.3 |

**320px 寬視窗下：一格 27 CSS px，畫面同時可見約 11.9 × 21 格。**

### 1.3 tile 尺寸的決定邏輯【讀碼】

`src/render/camera.ts`：

```ts
const TARGET_TILES_ACROSS = 12;   // 以畫布短邊為準
const MIN_TILE = 18;
const MAX_TILE = 46;
tile = round(clamp(min(viewW, viewH) / 12, 18, 46))
```

所以 tile 的 CSS 尺寸恆在 18–46 之間，橫向可見格數幾乎固定是 12（平板因為短邊是寬度而變成 16.7）。

### 1.4 建議的來源尺寸：**128 × 128**【推論】

- 實測最大裝置像素／格 = 92（平板）。
- 理論最大 = `MAX_TILE 46 × DPR上限 2.5` = **115**。
- 因此 **128px 來源永遠不會被放大**，且是 2 的冪次，對圖集打包友善。

要不要另外出 64px？

| 方案 | 優點 | 缺點 |
|---|---|---|
| 只出 128 | 流程單純、永不模糊 | 在 320px 手機上要縮到 54px（2.37× 縮小），canvas 2D 只有雙線性、沒有 mipmap，細節多的貼圖會有摩爾紋與閃爍 |
| 出 64 + 128 兩套 | 各解析度都接近 1:1，最銳利 | 檔案數與 manifest 複雜度加倍 |

**建議：先只出 128，但把貼圖畫得「低頻」**——避免 1px 細節與高頻雜訊，縮小才不會閃。
若試玩後發現小螢幕上有摩爾紋，再補 64px 那一套；manifest 應預留 `variants` 欄位以免屆時要改格式。

## 2. 體積與載入預算

### 2.1 目前的量【實測】

| 檔案 | 原始 | gzip | 線上實際傳輸 |
|---|---|---|---|
| `index-*.js` | 59,872 | 21,544 | 21,652（gzip） |
| `index-*.css` | 7,481 | 2,205 | — |
| `index.html` | 3,100 | 1,382 | — |
| **合計** | **70,453** | **≈25,100** | — |

線上確認 `Content-Encoding: gzip`、`Vary: Accept-Encoding`；**沒有 brotli**。

### 2.2 建議上限：**首屏總下載 ≤ 400 KB（壓縮後）**【推論】

依據：這是一個沒有安裝步驟的手機網頁遊戲，使用者的耐心以「第一次點連結到能動」計。

- 以 4G 中位速率（保守取 1.5 MB/s 有效吞吐、RTT 100ms）估算，400 KB 約 0.4–0.8 秒下載，
  加上 TLS 與 DNS，**一秒內可開始玩**。【推論】
- 目前 25 KB，等於留了約 **375 KB 給美術**。

這個上限相當寬。實際上按 §7 的清單，全部資產用 WebP 有損只需要 **20–65 KB**，
連預算的兩成都用不到。**體積不是這個專案的瓶頸**——瓶頸是可讀性（§5）。

### 2.3 GitHub Pages 的快取行為【實測】

```
index.html         Cache-Control: max-age=600   ETag: "6a8f8ef2-c1c"
assets/index-*.js  Cache-Control: max-age=600   ETag: "6a8f8ef2-ea05"
```

**帶內容雜湊的資產也只有 600 秒。** 這是 GitHub Pages 的固定行為，repo 這邊無法設定標頭。

後果：

- 10 分鐘內重複造訪 → 走記憶體／磁碟快取，零請求。
- 超過 10 分鐘 → 每個檔案都要發一次條件式請求（帶 `If-None-Match`），
  拿 304 雖然省下 body，但**每個檔案都要一次 RTT**。散檔越多，這個成本越明顯。

**service worker 值得加嗎？【推論】**

值得，但理由不是省流量，而是**省 RTT 與離線可用**：

- 用 cache-first 策略把 `art/*` 永久快取（檔名帶雜湊時可以安全這麼做），
  重複造訪的美術請求數歸零。
- 對一個回合制單機遊戲，離線可玩是實質好處。
- 成本：一個約 60 行的 SW + 註冊碼。

**但建議排在資產真的進來之後再做**，現在 25 KB 的站台加 SW 是提前優化。
同時它也會與 CI 的「線上健檢」互動（SW 可能讓健檢抓到舊版），加的時候要一起處理。

## 3. 格式與圖集

### 3.1 格式：**WebP，不做 fallback**【外部】【推論】

| 格式 | 行動端支援 | 相對體積 |
|---|---|---|
| PNG-8 | 全部 | 基準 |
| WebP | iOS Safari 14+（2020-09）、Chrome 全部；全球約 96% | 約 PNG-8 的 35–50% |
| AVIF | iOS Safari 16.4+（2023-03）、Chrome 85+；全球約 95–98% | 再省約 25–30% |

本專案的目標平台是 iOS Safari 與 Android Chrome。**建議單一採用 WebP，不做 fallback。**

不選 AVIF 的理由【推論】：全部資產只有 20–65 KB，AVIF 再省下來的絕對量約 10 KB，
換來的是 iOS 16.4 以下裝置整個開不了圖、以及低階裝置較慢的解碼。
在這個量級上，**簡單比省 10 KB 重要**。

若哪天資產量長到數百 KB（例如加入逐格動畫或多張地圖），再重新評估 AVIF。

### 3.2 圖集 vs 散檔：**這個規模用散檔**【推論】

本專案的資產總數（§7）約 **12–15 張**。

- Canvas 2D 的 `drawImage` **沒有 GPU 換紋理的成本**，圖集在這裡不會帶來繪製效能好處
  （那是 WebGL 的考量）。
- 圖集唯一的實質好處是減少 HTTP 請求數 —— 而 §2.3 說明 GitHub Pages 每 10 分鐘就要
  重新驗證，15 個請求 vs 1 個請求確實有差。
- 但圖集會讓資產替換變麻煩（改一張要重打包），而這個專案的美術是**外部流程產出、逐張提交**的。

**結論：散檔 + 一份 manifest。** 若之後請求數變成問題，優先用 service worker 解決（§2.3），
而不是引入打包步驟——因為建置流程明確不得產生資產（見任務前提）。

### 3.3 尺寸與記憶體上限【外部】

| 限制 | 數值 |
|---|---|
| iOS Safari 單一 canvas 面積上限（iOS 18.0 前） | 16,777,216 px（4096×4096） |
| iOS Safari 單一 canvas 面積上限（iOS 18.0 起） | 67,108,864 px（8192×8192） |
| iOS Safari canvas 總記憶體上限 | 約 384 MB（Safari 15；隨版本與裝置而異） |

本專案的 canvas backing store 最大實測是 **1536×2048 = 3.1M px**（平板），
離 16.7M 的舊上限還有 5 倍餘裕。【實測】

**圖集尺寸上限建議：2048×2048。**【推論】
即使將來改用圖集，2048² = 4.2M px，在最保守的 iOS 上限內仍有 4 倍空間，
且遠低於任何行動 GPU 的紋理上限。單張 128px tile 完全不受限。

## 4. 現有渲染層體檢

### 4.1 繪製順序與圖層【讀碼】

`src/render/renderer.ts` 的 `draw()` 是唯一的入口，順序固定：

| # | 函式 | 畫什麼 | 貼圖化？ |
|---|---|---|---|
| 0 | `ctx.fillRect` | 背景底色 | **會被取代** |
| 1 | `drawTiles` | 地形（地板／格線／牆／半身掩體／三種目標物底色與字符）＋ 視野明暗疊層 | **會被取代** |
| 1b | `drawVoid` | 界外岩層斜紋 | **會被取代** |
| 2 | `drawMapEdge` | 可作戰範圍虛線外框 | 維持圖元 |
| 3 | `drawCorpses` → `drawCorpse` | 屍體 X 與「有裝備」黃點 | **會被取代** |
| 4 | `drawGhosts` | 最後已知位置的虛線圈 + `?` | **兩者疊加** |
| 5 | `drawUnits` → `drawUnit` | 單位本體（圓／方／菱／三角）、蹲姿橫線、HP 條、AI 狀態字符、「剛發現」字樣、選取環 | **兩者疊加** |
| 6 | `drawMovePreview` | 路徑點、終點框、AP 標籤 | 維持圖元 |
| 7 | `drawInteractPreview` | 互動框與標籤 | 維持圖元 |
| 8 | `drawTargetFrames` | 合法目標細框、非 IDLE 點滅框／剛發現虛線框 | 維持圖元 |
| 9 | `drawLock` | 雷射線、紅點準星、掩蔽成因框、資訊標籤 | 維持圖元 |
| 10 | `drawVignette` | 邊角壓暗 | 維持圖元 |
| 11 | `EffectLayer.draw`（由 `game.ts` 在 `draw()` 之後呼叫） | 噪音菱形、彈道、狀態提示、浮動數字 | 維持圖元 |

**「兩者疊加」的意思**：單位本體換成貼圖，但 HP 條、AI 狀態、選取環、蹲姿指示仍然是圖元，
疊在貼圖上。這是刻意的——那些是資訊層，不該被美術風格綁架（見 §5）。

### 4.2 繪製呼叫已經收斂，不是散落各處【讀碼】

實測統計每個函式的 canvas API 呼叫數：

| 函式 | ctx 呼叫數 | 主要原語 |
|---|---|---|
| `drawUnit` | 43 | `lineTo`×6, `beginPath`×3, `arc`×2, `stroke`×2 |
| `drawLock` | 34 | `beginPath`×4, `setLineDash`×4, `stroke`×3 |
| `drawLabel` | 26 | `arcTo`×4, `fillText`×2 |
| `drawTiles` | 15 | `fillRect`×6, `strokeRect`×1 |
| `drawGhosts` | 15 | `setLineDash`×2, `arc`×1 |
| `drawCorpse` | 13 | `beginPath`×2, `moveTo`×2, `lineTo`×2 |
| `drawTargetFrames` | 11 | `strokeRect`×2, `setLineDash`×2 |
| 其餘 8 個 | 2–10 各 | |

**關鍵發現：所有 canvas 呼叫都在 `render/` 底下的這 14 個函式內，`ui/` 與 `core/` 完全沒有直接呼叫 canvas API。**
（`ui/game.ts` 只碰 `getContext` 與 `setTransform`，屬於初始化。）

而且**每一種視覺元素只有一個繪製點**：地形只在 `drawTiles`、單位只在 `drawUnit`、屍體只在 `drawCorpse`。

### 4.3 資產層該接在哪裡【推論】

新增 `src/render/assets.ts`，職責：載入 manifest、快取 `HTMLImageElement`／`ImageBitmap`、
提供 `sprite(name): CanvasImageSource | null`。回傳 `null` 時呼叫端走現有的圖元繪製當 fallback。

要動的地方只有**三個函式的內部**，簽章與呼叫關係完全不變：

```ts
// drawTiles 內，畫地板／牆／掩體的那幾行
const img = assets.sprite(kindToName(kind));
if (img) ctx.drawImage(img, s.x, s.y, t, t);
else { /* 現有的 fillRect 路徑原封不動保留 */ }

// drawUnit 內。第二個參數就是 §8.3 的面向鉤子 ——
// 現在一定會退回無後綴的圖，但呼叫端寫法從第一天就是最終形態。
const img = assets.sprite(unitSpriteName(u), u.facing);
```

`drawCorpse` 同理。

**目前完全沒有 `drawImage`、`createPattern` 或 `new Image()`**【實測：全 repo grep 為 0】，
所以這是純粹的新增，不是改寫。

### 4.4 重構規模量化【推論】

| 工作 | 檔案 | 規模 |
|---|---|---|
| 資產載入器 | 新增 `src/render/assets.ts` | 約 80–120 行 |
| manifest 型別與載入 | `src/core/content.ts` 或獨立 | 約 20 行 |
| 地形貼圖化 | `drawTiles` + `drawVoid` | 改動約 20 行 |
| 單位貼圖化 | `drawUnit` | 改動約 15 行（只換本體，資訊層不動） |
| 屍體貼圖化 | `drawCorpse` | 改動約 10 行 |
| 載入進度／首次繪製時機 | `src/ui/game.ts` | 約 20 行 |
| 測試 | 新增 `assets.test.ts` | 約 60 行 |

**合計約 250 行新增、45 行改動，不動任何既有函式簽章。**
以本專案目前 2,033 行的 render+ui 規模來說，是一次中小型改動。

### 4.5 對 v0.4 事件驅動架構的影響：**沒有**【讀碼】【推論】

`CombatEvent` 是規則層吐出的純資料，`EffectLayer` 消費它來播動畫。
資產層只影響「怎麼畫一個東西」，不影響「什麼時候該畫什麼」。

- `core/` 不需要任何改動。
- `GameState` 仍然不含任何動畫或資產狀態。
- `EffectLayer` 的浮動數字、彈道、噪音環全部是圖元，**不需要貼圖也不該貼圖化**（§5）。

唯一的互動點是**時序**：資產是非同步載入的，而 `game.ts` 的 rAF 迴圈第一幀就會繪製。
處理方式是 fallback 路徑（圖未載入 → 畫圖元），這樣載入中與載入失敗都不會出現空白畫面，
也不需要 loading 畫面。【推論】

## 5. 可讀性衝突分析

**這一節是本文件最重要的部分。導入美術最常見的失敗不是畫得不好看，而是資訊層讀不到了。**

### 5.1 先講結論：目前是靠描邊撐住的，不是靠地形夠暗【實測】

把現有資訊層的顏色，對現有**最亮的地形色**（半身掩體頂 `#84d69b`，相對亮度 0.554）算對比：

| 資訊元素 | 對比 | |
|---|---|---|
| 尋路路徑點 `#4fd6ff` | 1.00:1 | ❌ |
| 玩家單位 `#4fd6ff` | 1.00:1 | ❌ |
| 「擋下 N」`#7fd0e8` | 1.02:1 | ❌ |
| 掩蔽成因框 `#7fd0e8` | 1.02:1 | ❌ |
| 空倉／警戒 `#ffb648` | 1.03:1 | ❌ |
| 未命中 `#c3ccd5` | 1.05:1 | ❌ |
| 被擋下數字 `#9db4c8` | 1.26:1 | ❌ |
| 合法目標框 `#d2e6f5` | 1.33:1 | ❌ |
| 傷害數字 `#ffe6a3` | 1.39:1 | ❌ |
| 噪音環 `#b48ce0` | 1.59:1 | ❌ |
| 擊殺 `#ff6a58` | 1.66:1 | ❌ |
| 警戒框 `#ff5b4a` | 1.80:1 | ❌ |
| 雷射線 `#ff4d3d` | 1.93:1 | ❌ |

**全部低於 3:1。** 那為什麼現在看起來沒問題？兩個原因【讀碼】：

1. `#84d69b` 只是掩體格頂端 **11% 高度的一條細線**，不是整格填滿。實際占大面積的地形
   是地板（亮度 0.023）與牆面（0.092）。
2. **所有文字都有深色描邊**：`effects.ts` 的 `outlinedText()` 與 `renderer.ts` 的
   `drawLabel()` 都先用 `rgba(4,6,9,0.92)` 描一圈再填色；HP 條有 `rgba(0,0,0,0.6)` 底襯。

換句話說，**現在的可讀性是「地形剛好很暗」加「文字有描邊」的疊加結果，
而前者一旦換成有紋理、有明暗變化的貼圖就不成立了。**

### 5.2 逐項體檢

「靠什麼辨識」欄決定了它在紋理背景上的存活能力：靠**形狀**的最耐、靠**亮度**次之、
純靠**顏色**的最脆弱（因為紋理會同時改變背景的亮度與色相）。

| 資訊元素 | 靠什麼辨識 | 有描邊/底襯？ | 換成貼圖後 | 建議 |
|---|---|---|---|---|
| 浮動傷害數字 | 顏色 + 文字形狀 | ✅ 描邊 | 安全 | 維持 |
| 「未命中」文字 | 顏色 + 文字 | ✅ 描邊 | 安全 | 維持 |
| 「擋下 N」副標 | 顏色 + 文字 | ✅ 描邊 | 安全 | 維持 |
| 「剛發現」字樣 | 顏色 + 文字 | ✅ 描邊 | 安全 | 維持 |
| 資訊標籤（命中率／傷害／裝甲） | 文字 | ✅ 深色圓角底襯 | 安全 | 維持 |
| HP 條 | 亮度 + 位置 | ✅ 深色底襯 | 安全 | 維持 |
| **合法目標細框** | **亮度**（近白細線） | ❌ | **危險**：亮地形上直接消失 | **加深色外描邊** |
| **非 IDLE 點滅框** | 顏色 + **動態** | ❌ | 中等：靠閃爍還能被注意到，但顏色會被吃掉 | **加深色外描邊** |
| **剛發現虛線框** | 顏色 + 虛線節奏 | ❌ | 中等 | **加深色外描邊** |
| **雷射瞄準線** | 顏色（紅） | ❌ | **危險**：紅色地形上完全消失 | **雙線：深色底 + 亮色芯** |
| **紅點準星** | 顏色 + 形狀 | ❌ | 中等 | 加深色外環 |
| **掩蔽成因框** | 顏色（青） | ❌ | **危險**——而這是 §12.10 的教學重點 | **加深色外描邊** |
| **尋路路徑點** | 顏色（青） | ❌ | **危險** | 加深色外描邊或改用深色鑲邊圓點 |
| **單位本體** | 形狀 + 顏色 | ❌ | 中等：形狀救得回來，但貼圖化後形狀由美術決定 | **貼圖須自帶深色外輪廓** |
| **屍體 X** | 亮度（暗褐 `#6d5a52`） | ❌ | **已經是現在最弱的一環**：對地板只有 2.2:1、對牆頂 1.45:1 | **提亮 + 加描邊，或改成有底襯的圖示** |
| **幽靈虛線圈 + `?`** | 顏色 + 虛線 | ❌ | 危險 | 加描邊 |
| **敵人 `!` / `?` 字符** | 顏色 | ❌ | 危險 | 加描邊（「剛發現」那條已經有了，另兩個沒有） |
| **噪音菱形** | 顏色 + 動態擴張 | ❌ | 中等：靠動態還能被看到 | 可接受，必要時加深色底線 |
| 空投點／終端／補給箱 | 顏色底 + 字符 + 外框 | 半：有自己的色底 | 中等：貼圖化後底色由美術決定 | **字符加描邊；外框保留為圖元** |
| 地圖邊界虛線 | 亮度 | ❌ | 危險 | 加深色底線 |
| 玩家防禦狀態 | HUD 文字 | ✅ 在 DOM 上 | 完全不受影響 | 維持 |

### 5.3 地形貼圖的明度上限（由資訊層反推）【實測】

對每個**沒有描邊**的元素，解「要維持 3:1 圖形對比，背景最亮能到多少」：

| 元素 | 前景亮度 | 地形亮度上限 | 約 L* |
|---|---|---|---|
| 屍體 X | 0.112 | 0.004 | 4 |
| 地圖邊界虛線 | 0.190 | 0.030 | 20 |
| 射手型單位 | 0.251 | 0.050 | 27 |
| 雷射線 | 0.269 | 0.056 | 28 |
| 警戒框／衝鋒型／幽靈 | 0.292 | 0.064 | 30 |
| 噪音菱形 | 0.338 | 0.079 | 34 |
| 裝甲型單位 | 0.364 | 0.088 | 36 |
| 剛發現框／掩蔽成因框 | 0.55 | 0.151 | 46 |
| 路徑點／玩家 | 0.570 | 0.157 | 47 |
| 合法目標細框 | 0.769 | 0.223 | 54 |

對照現有地形亮度：地板 0.023（L* 17）、牆面 0.092（L* 36）、牆頂 0.185（L* 50）。

**「屍體 X」把上限壓到 L* 4，等於什麼貼圖都不能用。** 它是現在就已經不合格的一環——
在現有地板上只有 2.2:1，在牆頂上甚至比背景更暗（1.45:1）。

**若先把屍體處理掉（提亮或加描邊），地形上限放寬到亮度 0.030、約 L* 20。**
這仍然很嚴苛（比現在的牆面還暗）。

### 5.4 兩條路，建議走第二條【推論】

**路線 A：地形壓在 L* ≤ 20。** 資訊層一行不用改，但地形只能是幾乎全黑的貼圖，
等於花了美術成本卻看不出質感。**不建議。**

**路線 B：先替沒有描邊的元素補上深色描邊／底襯，再放寬地形。** 【建議】

描邊色 `rgba(4,6,9,0.92)`（亮度 0.0018）對地形的對比【實測】：

| 地形亮度 | L* | 描邊對地形對比 |
|---|---|---|
| 0.20 | 52 | 1.6:1 |
| 0.40 | 69 | 3.5:1 |
| 0.60 | 82 | 7.1:1 |
| 0.80 | 92 | 12.6:1 |

描邊本身在**亮**地形上很好認；在中間調（L* 50 上下）最弱。
因此即使補了描邊，地形仍應避免長時間停在 L* 45–60 的中灰。

**路線 B 之下的地形明度規範：**

- **大面積（>25% tile 面積）：L\* 12–40**（相對亮度 0.014–0.11）。
  這一段同時避開「太亮吃掉資訊層」與「中灰讓描邊失效」。
- **亮部高光：允許到 L\* 75，但面積必須 ≤ 15% tile**。
  這正是現在半身掩體頂那條 11% 亮線的做法，證明可行。
- **暗部：不低於 L\* 8**，否則與界外岩層（L* 5）混淆。

### 5.5 彩度與色相保留區【推論】

現有地形的彩度：地板 19%、牆面 15%、牆頂 14%、掩體底 23%（近中性）；
目標物底色 57–60%（本來就是資訊性的色塊）。

資訊層佔用的色相很集中：

| 色相 | 目前用途 | 地形必須讓開 |
|---|---|---|
| 青／天藍 `#4fd6ff` `#7fd0e8` | 玩家、路徑、掩蔽成因、擋下註記 | ✅ |
| 紅／橘紅 `#ff5b4a` `#ff4d3d` `#ff6a58` | 警戒、雷射、擊殺、衝鋒型 | ✅ |
| 琥珀 `#ffb648` `#ffe6a3` | 剛發現、空倉、傷害數字 | ✅ |
| 薄荷綠 `#5cf0cd` | 目標完成 | ✅ |
| 紫 `#b48ce0` `#b06be0` | 噪音、射手型 | ✅ |

**規範：地形貼圖的彩度上限 25%（HSL S）**，且避免上表五個色相的高彩度使用。
可用的地形色域是**去飽和的藍灰、青灰、暖褐灰、橄欖灰**——
這與現有調色盤一致（現有地形彩度 14–23%），所以不是新的限制，只是把它寫下來。

目標物底色（空投點／終端／補給箱）是例外：它們本來就是資訊色塊，
若要貼圖化，應保留現有的高彩度色底或改以圖元外框補強。

### 5.6 建議搬離地形的資訊【推論】

大部分資訊本來就該畫在戰場上（那是 v0.4 §2.1 的核心原則：不用開日誌就能理解戰況）。
只有兩項適合調整：

1. **屍體標示**：現在是純線條 X，最弱的一環。建議改成**有深色底襯的小圖示**
   （像目標物那樣有自己的色底），而不是靠線條顏色。
2. **敵人 `!` / `?` 狀態字符**：建議與「剛發現」一致，加上描邊。
   不必搬到 HUD——搬走反而會破壞「警戒狀態畫在敵人身上讓噪音因果可見」的設計價值。

**不建議搬走的**：浮動數字、目標框、雷射線、掩蔽成因框。
它們的價值就在於「和戰場位置綁在一起」，搬到 HUD 等於毀掉 v0.4 與 v0.5 的設計意圖。

## 6. 動畫能力

### 6.1 現有架構支援到什麼程度【讀碼】

`EffectLayer`（`src/render/effects.ts`）已經是一個時間軸驅動的動畫系統：

- 每個效果記 `born` 時戳，`draw(ctx, cam, now)` 依 `now - born` 算出進度，
  超過壽命自動移除（`FLOAT_MS 750` / `TRACER_MS 190` / `RING_MS 520` / `PIP_MS 700`）。
- `game.ts` 的 rAF 迴圈每幀呼叫 `draw(now)`，`now` 來自 `requestAnimationFrame` 的時戳。

因此**已經支援**：位移、淡入淡出、縮放、依時間的幾何變形（噪音菱形就是擴張動畫）。

**逐格動畫需要補的**：一個「單位動畫時鐘」。現有的 `EffectLayer` 是**一次性效果**的容器
（事件觸發 → 播完消失），而角色的待機／行走是**持續狀態**，需要不同的生命週期管理。
估計新增 40–60 行【推論】。

`GameState` 不需要任何改動——動畫時鐘和效果一樣屬於渲染層。

### 6.2 逐格動畫的代價【推論】

以每個單位 4 幀估算。面向要算八向而不是四向（理由見 §7.2）：

| 內容 | 張數 | WebP 有損 q80 |
|---|---|---|
| 靜態單張（無面向） | 5 | 約 11 KB |
| 加八向面向 | 40 | 約 88 KB |
| 八向 × 4 幀逐格 | 160 | 約 352 KB |

記憶體：160 張 128×128 RGBA 解碼後約 **10.5 MB**。
相對 iOS 的 384MB canvas 記憶體上限微不足道【外部】，不構成問題。

體積與記憶體都不是問題。真正的成本一是**玩家的等待時間**（§6.3 第 1 點），
二是**美術工時**：張數從 5 張變成 160 張，是 32 倍。

### 6.3 判斷：**不做逐格動畫**【推論】

理由依重要性排序——**最硬的一條是等待成本，不是製作成本**：

1. **等待時間會複利。** v0.6 已經加了敵人回合逐一演出，每個動作間隔 200ms
   （`presentation.enemyStepMs`）。逐格動畫疊在上面，每個動作的視覺長度又拉長一截，
   十隻敵人的回合會變得難以忍受。
   **回合制玩家會狂點畫面**——v0.6 特地做了「點畫面跳過演出」正是承認了這件事。
   在一個玩家想加速的地方加動畫，動畫只會變成擋路的東西。
2. **回合制沒有連續運動可演。** 單位一次移動一格，過渡只有約 110ms
   （`presentation.playerMoveStepMs`）。四幀行走循環在 110ms 內根本播不完一輪。
3. **場上單位小。** 一格在手機上只有 27–46 CSS px，四幀的差異在這個尺寸下幾乎看不出來。
4. **回饋層已經承擔了「動起來」的職責。** 傷害數字、彈道、噪音環、狀態提示都會動。
5. 16 倍的美術工時只是最後一根稻草，不是主要理由。

**建議的動畫層次（依投資報酬排序）：**

1. **單位靜態貼圖 + 現有的程式化動態**（受擊時的位移抖動、死亡時的淡出）——
   幾乎免費，用現有 `EffectLayer` 就能做。
2. **兩幀待機**（呼吸／閒置微動），張數只加倍。若試玩覺得畫面太死再考慮。
3. 四幀行走：**除非之後改成即時制或加入更長的移動動畫，否則不要做。**

## 8. 資產製作規範

> 這一節是給美術流程直接照著執行的。以上調查的結論全部收斂到這裡。

### 8.1 尺寸與格式

| 項目 | 規範 |
|---|---|
| 來源尺寸 | **128 × 128 px**，正方形，一格一張 |
| 格式 | **WebP，有損 q80**（不需要 PNG fallback） |
| 色彩空間 | sRGB |
| Alpha | 單位／屍體需要透明背景；地形不要透明（整格填滿） |
| 單張上限 | 8 KB（超過表示細節過多，見下方「低頻」要求） |
| 總量上限 | 全部資產壓縮後 **≤ 200 KB** |

**「低頻」要求**：貼圖會被縮到 54–92 裝置像素（縮小率最高 2.37×），
而 canvas 2D 沒有 mipmap。避免 1–2px 的細節、高頻雜訊、細密網格——它們縮小後會閃爍。
把細節做在**大塊的明暗與剪影**上。

### 8.2 色彩與對比限制（硬性）

| 規範 | 值 | 理由 |
|---|---|---|
| 地形大面積明度 | **L\* 12–40** | 上限避免吃掉資訊層；下限避免與界外岩層混淆 |
| 地形亮部高光 | 最高 L\* 75，但**面積 ≤ 15% tile** | 現有半身掩體頂的 11% 亮線證明可行 |
| 地形彩度 | **HSL S ≤ 25%** | 與現有地形（14–23%）一致 |
| 避免中灰 | 盡量不要大面積停在 **L\* 45–60** | 深色描邊在這一段對比最弱（1.6:1） |
| 保留色相 | 青／天藍、紅／橘紅、琥珀、薄荷綠、紫 **不得高彩度使用** | 這五個色相已被資訊層佔用 |
| 單位貼圖 | **必須自帶 1–2px 深色外輪廓** | 單位要疊在地形貼圖上，不能只靠色塊區分 |

可用的地形色域：**去飽和的藍灰、青灰、暖褐灰、橄欖灰。**

### 8.3 命名與擺放

#### 命名慣例（**面向的位置現在就先留著**）

```
<類別>_<主體>[_<狀態>][_<面向>]
```

- 類別：`terrain` / `unit` / `prop`
- 面向（**目前一律省略**）：`n` `ne` `e` `se` `s` `sw` `w` `nw`
- 全小寫、底線分隔、不含版本號或日期（版本由 git 管）

```
public/art/
  manifest.json
  terrain_floor.webp        terrain_wall.webp        terrain_half_cover.webp
  terrain_void.webp         terrain_drop_point.webp  terrain_drop_point_start.webp
  terrain_terminal.webp     terrain_terminal_done.webp
  terrain_supply.webp       terrain_supply_done.webp
  unit_soldier_stand.webp   unit_soldier_crouch.webp
  unit_runner.webp          unit_hulk.webp           unit_shooter.webp
  prop_corpse.webp
```

**邏輯名稱 = 檔名去掉副檔名。** 不用子目錄——資產總數只有 16–18 張，
攤平之後「名稱」與「檔案」一一對應，沒有路徑與鍵值兩套寫法的問題。

#### 面向的解析順序（這就是那個鉤子）

資產層查表時走一條**回退鏈**：

```
sprite("unit_soldier_stand", facing="ne")
  → 先找 unit_soldier_stand_ne
  → 找不到就退回 unit_soldier_stand
  → 再找不到就回傳 null（呼叫端畫圖元）
```

這條規則現在就要寫進載入器，即使目前一張帶面向的圖都沒有。它帶來三件事：

1. **今天交的 `unit_soldier_stand.webp` 永遠有效。** 將來補
   `unit_soldier_stand_n.webp` 等八張時，是**新增檔案**，不動既有素材、
   不改 manifest 格式、不改載入器。
2. **面向可以分批交。** 只畫了 `_n` 與 `_s`？另外六向自動退回無面向版本，
   畫面不會破。
3. **狀態與面向正交。** `unit_soldier_crouch_n` 這種組合天然成立，
   不需要為每個組合另外定義名稱。

> 為什麼不是現在就叫 `unit_soldier_stand_any`？
> 因為那會讓「今天的素材」帶著一個將來沒有意義的後綴，
> 而回退鏈已經讓無後綴的名稱扮演「通用版本」的角色，語意更乾淨。【推論】

#### 為什麼放 `public/`

【推論】Vite 會把 `public/` 原樣複製、不加雜湊、不進 JS bundle。
代價是這些檔案拿不到內容雜湊檔名，配合 GitHub Pages 的 `max-age=600`（§2.3）
就是每 10 分鐘要重新驗證一次——這正是 service worker 要解決的問題。
若之後改用雜湊檔名，manifest 需要改由建置產生，與「建置不得產生資產」的前提衝突，
所以維持 `public/`。

### 8.4 manifest 格式

`public/art/manifest.json`：

```json
{
  "version": 1,
  "tileSize": 128,
  "sprites": {
    "terrain_floor":          { "src": "terrain_floor.webp" },
    "terrain_wall":           { "src": "terrain_wall.webp" },
    "terrain_half_cover":     { "src": "terrain_half_cover.webp" },
    "terrain_void":           { "src": "terrain_void.webp" },
    "terrain_drop_point":       { "src": "terrain_drop_point.webp" },
    "terrain_drop_point_start": { "src": "terrain_drop_point_start.webp" },
    "terrain_terminal":       { "src": "terrain_terminal.webp" },
    "terrain_terminal_done":  { "src": "terrain_terminal_done.webp" },
    "terrain_supply":         { "src": "terrain_supply.webp" },
    "terrain_supply_done":    { "src": "terrain_supply_done.webp" },
    "unit_soldier_stand":     { "src": "unit_soldier_stand.webp" },
    "unit_soldier_crouch":    { "src": "unit_soldier_crouch.webp" },
    "unit_runner":            { "src": "unit_runner.webp" },
    "unit_hulk":              { "src": "unit_hulk.webp" },
    "unit_shooter":           { "src": "unit_shooter.webp" },
    "prop_corpse":            { "src": "prop_corpse.webp" }
  }
}
```

將來補面向時，只是往 `sprites` 多加幾筆，既有的條目一個字都不用改：

```json
    "unit_soldier_stand":    { "src": "unit_soldier_stand.webp" },
    "unit_soldier_stand_n":  { "src": "unit_soldier_stand_n.webp" },
    "unit_soldier_stand_ne": { "src": "unit_soldier_stand_ne.webp" },
```

設計原則：

- **manifest 是唯一的真相來源。** 遊戲只讀 manifest，不去猜檔名。
- **缺項是合法的。** manifest 裡沒有的名稱 → 資產層回傳 `null` → 走現有圖元繪製。
  這讓美術可以一張一張交，不必等全部到齊。
- `variants` 欄位**現在不要加**，但格式預留了空間（每個 sprite 是物件而非字串），
  日後要加 64px 版本時不用改結構。
- **面向不是 manifest 的欄位，而是名稱的一部分**（§8.3 的回退鏈）。
  這樣「補面向」永遠只是新增鍵值，不會變成 schema 遷移。

### 8.5 驗收自檢（交件前跑一次）

1. 每張 128×128、WebP、≤ 8 KB。
2. 用取色器抽樣：大面積區域的 L* 落在 12–40，彩度 ≤ 25%。
3. 亮部（L* > 60）的面積目測 ≤ 15%。
4. 把貼圖縮到 54px 檢查有沒有閃爍或摩爾紋。
5. 單位貼圖放在最亮與最暗的地形上各看一次，剪影都要認得出來。
6. 檔名符合 §8.3 的 `<類別>_<主體>[_<狀態>][_<面向>]` 慣例，
   **目前一律不帶面向後綴**（那個位置是留給將來的）。

## 9. 導入計畫

### 9.1 前置：先修可讀性，再進美術【建議】

§5 的結論是：**在資產進來之前，先把沒有描邊的資訊元素補上描邊。**
否則第一張地形貼圖一進來，目標框、雷射線、掩蔽成因框就會開始消失，
而那時很難分辨是「美術太亮」還是「資訊層本來就脆弱」。

這一步不需要任何資產，是純渲染層改動：

| 工作 | 檔案 | 規模 |
|---|---|---|
| 抽一個 `outlinedStroke()` helper | `renderer.ts` | 約 15 行 |
| 目標框、雷射線、準星、掩蔽成因框、路徑點、幽靈、邊界虛線加描邊 | `renderer.ts` | 約 6 處，各 2–3 行 |
| 敵人 `!` / `?` 字符加描邊 | `renderer.ts` `drawUnit` | 約 5 行 |
| 屍體改為有底襯的圖示 | `renderer.ts` `drawCorpse` | 約 10 行 |
| 對比回歸測試（用 `effects.test.ts` 的假 ctx 手法） | 新增 | 約 40 行 |

**建議排在下一個版本，與美術資產脫鉤。** 它本身就會讓現在的畫面更清楚。

### 9.2 資產層導入

| 階段 | 工作 | 檔案 | 規模 |
|---|---|---|---|
| A | 資產載入器 + manifest 載入 + `sprite()` 查詢 + **面向回退鏈（§8.3）** + 缺圖 fallback | 新增 `src/render/assets.ts` | 80–120 行 |
| A | 在 `game.ts` 啟動時非同步載入，不阻塞第一幀 | `src/ui/game.ts` | 約 20 行 |
| A | 測試：缺圖時不崩、manifest 缺項回 `null`、**面向回退鏈正確**（有 `_n` 用 `_n`、沒有就退回無後綴） | 新增 `tests/assets.test.ts` | 約 60 行 |
| B | 地形貼圖化 | `renderer.ts` `drawTiles` / `drawVoid` | 改 20 行 |
| C | 單位貼圖化（**只換本體，HP 條與狀態指示維持圖元**） | `renderer.ts` `drawUnit` | 改 15 行 |
| D | 屍體貼圖化 | `renderer.ts` `drawCorpse` | 改 10 行 |
| E | service worker（cache-first 快取 `art/*`） | 新增 + `main.ts` | 60–80 行 |

**A–D 合計約 250 行新增、45 行改動**，不動任何函式簽章、不動 `core/`、不動事件架構。

### 9.3 排序建議

1. **§9.1 可讀性補強** ← 先做，與美術無關
2. **階段 A** 資產層骨架 ← 可以在沒有任何圖檔的情況下完成並合併（fallback 保證行為不變）
3. **階段 B** 地形 ← 第一批美術，也是最容易破壞可讀性的一批，要單獨驗
4. **階段 C／D** 單位與屍體
5. **階段 E** service worker ← 等資產真的有量了再做，同時要處理它與 CI 線上健檢的互動

### 9.4 每一階段的驗收

- **A**：manifest 缺項、圖檔 404、載入中三種情況都必須畫出與現在完全相同的畫面。
  面向回退鏈要在**還沒有任何面向素材**的情況下就先寫好並測過——
  這是給「面向將來會變成規則」預留的鉤子（§7.2），
  等到真的要補面向時才寫，就會變成連基礎素材一起重做。
- **B**：在 320px 視窗下，§5.2 表中所有「危險」項目仍然可辨識。
- **C**：單位剪影在最亮與最暗地形上都認得出來；HP 條與狀態指示未被貼圖蓋住。
- **E**：CI 的線上健檢（比對 commit SHA）仍然通過——SW 不得讓健檢抓到舊版。
