# 複製人 PMC 戰術 Roguelike — MVP

單場戰鬥的可玩驗證版。手機直向瀏覽器優先，TypeScript + Canvas 2D + Vite，零遊戲引擎相依。

**線上版（手機直接開）**：https://darkbearlab.github.io/PMC_roguelike/

推到 `main` 就會自動跑測試 → 建置 → 部署 → 線上健檢，手機重新整理即可拿到新版。
資產檔名帶 hash，不會吃到舊快取；戰鬥紀錄面板（右上的 `誌`）頂端顯示 `build <commit>`，
可以直接確認手機上跑的是哪一版。

規格書：[`clone-pmc-roguelike-mvp-spec.md`](clone-pmc-roguelike-mvp-spec.md)（v0.17，與實作同步）

```bash
npm install
npm run dev        # http://localhost:5173  （手機同網段可用 --host 顯示的網址開）
npm run test       # 477 個測試：core/ 規則層、UI 互動文法、整張正式地圖的整合測試
npm run typecheck
npm run build
npm run map:build  # 重新產生並驗證四張地圖，同時更新 docs/map-stats.md

# 瀏覽器上的驗收腳本（需要先 npm run build && npx vite preview --port 4188）
node scripts/a11y.mjs        # 48×48 觸控區、320px 版面、地圖可觸性
node scripts/verify.mjs      # 陣亡 → 增援 → 回去撿屍體的完整流程
node scripts/playthrough.mjs # 一般操作、序列動作、模式鍵
node scripts/company.mjs     # v0.16：公司 → 配裝 → 派遣 → 結算 → 重新載入
node scripts/present.mjs     # v0.17：動畫可打斷、攝影機只在必要時平移、選單規則
node scripts/pace.mjs        # v0.17：動畫對真實牆鐘時間的影響（三組旋鈕對照）
```

開啟遊戲會先進**公司畫面**（名冊、軍械庫、補給站、逐人配裝），
接合約 → 挑首發 → 打 → 結算套用回公司。狀態存在 `localStorage`。
`?seed=12345` 固定亂數種子（連同清單一起重現），
`?map=mission_04` **略過整個局外層**直接開圖（用測試用的派遣快照），
`?reset=1` 清除存檔。
開發者主控台會印出這批合約的地圖、當場的 seed 與地圖 id。

CI（`.github/workflows/deploy.yml`）在每次 push 到 `main` 時跑：
型別檢查 → 測試 → 「地圖 JSON 與 `scripts/build_map.mjs` 必須一致」→ 建置 → 部署 →
**線上健檢**（部署完直接抓線上頁面，確認它真的是這次的 commit）。

> 最後那一步是有原因的：GitHub 內建的 legacy Jekyll builder 曾經跟這個 workflow
> 搶著部署並且贏了，線上被換成 repo 根目錄那份**未經建置**的 `index.html`
> （script 還指著 `/src/main.ts`，於是整頁空白）。以前那是靜悄悄的，現在 CI 會直接變紅。
> 若真的再發生，去 **Settings → Pages** 把 Source 改回 **GitHub Actions**。

## 架構

```
src/
  core/          純函式規則層。不 import 任何 DOM / Canvas / 瀏覽器 API。
    state.ts       GameState 型別與唯讀選取器
    commands.ts    Command 型別、checkLegal()、applyCommand()   ← 規則層唯一入口
    los.ts         視線（對稱 Bresenham + 半身掩體規則）
    combat.ts      命中管線、傷害、濺射、噪音
    sight.ts       面向視野（半平面）與背刺判定 —— **不對稱**，與 los.ts 分開
    inventory.ts   背包、重量分級、彈藥堆疊
    scheduler.ts   行動排程器：誰下一個動、clock 怎麼推進
    sequence.ts    系列動作：可續行／須重來、消耗品的效果
    ai.ts          敵人狀態機、宣告下一個動作、口令
    contracts.ts   合約清單：標籤與難度由地圖統計值推導、可播種抽圖
    loadout.ts     配裝的重量與檢查（警告 vs 阻擋）
    meta.ts        局外層：名冊、軍械庫、共用庫存、派遣快照、結果套用
    weapon.ts      武器型號與實例：詞條套用點、決定性的實例識別碼
    tactics.ts     落點評分：掩體、側翼、射線（權重依原型）
    pathfind.ts    四方向 BFS 尋路
    rng.ts         可播種 xoshiro128**
    map.ts / setup.ts / content.ts / grid.ts / log.ts
  render/        Canvas 繪製與可見性快取，唯讀 GameState
    motion.ts      格間位移與攝影機平移。純呈現，GameState 裡沒有它的痕跡
  ui/            觸控輸入、HUD、浮動小卡、Modal、合約清單、公司畫面、存檔
  data/          rules / weapons / actors / items / callouts / maps/mission_01～04
                 contracts（手寫公文）/ contract-rules（標籤門檻與難度公式）
                 weapons 七把槍 / ammo 彈藥型別（引用口徑，不是拿口徑當彈藥）
```

### 四條硬性要求的落實方式

| 要求 | 做法 | 驗證 |
|---|---|---|
| `core/` 純且決定性 | `applyCommand(state, cmd) => newState`。內部先 `structuredClone` 再改複製品；非法指令回傳**原本那個物件**（identity 不變） | `determinism.test.ts` |
| 亂數一律經過 `core/rng.ts` | 產生器的完整內部狀態存在 `GameState.rng`（含 `count`），JSON 還原後可接著抽出相同序列 | `determinism.test.ts`（含掃描 `src/` 確認沒有 `Math.random()`） |
| 渲染／UI 唯讀 | 兩層都只讀 `GameState`，所有改動都發 Command。**鎖定狀態刻意留在 UI 層**，不污染規則層 | `determinism.test.ts` 掃描 `core/` 沒有瀏覽器 API |
| 狀態可完整序列化 | 沒有 Map / Set / class instance / 函式 | `determinism.test.ts` |

## 三件容易搞混的事：距離 vs 遮擋 vs 面向

「看得見嗎」是三個獨立的檢查，用三種算法，放在三個檔案裡。這是刻意的：

| 問題 | 用什麼算 | 對稱？ | 在哪裡 |
|---|---|---|---|
| 「夠不夠得到？」 | **曼哈頓距離** `\|dx\|+\|dy\|` | 是 | `core/grid.ts` |
| 「中間有沒有東西擋著？」 | **幾何直線**（對稱 Bresenham） | **是** | `core/los.ts`，一行都沒動 |
| 「我有沒有朝那邊看？」 | **半平面**（內積 ≥ 0） | **否** | `core/sight.ts`（v0.8 新增） |

對稱性是**遮擋**的正確性條件——非對稱視線是這類遊戲最常見的 bug。
不對稱則是**面向**的全部意義——背刺就是靠這個不對稱成立的。
三者混在同一個函式裡的話全都會壞掉。

專案裡 `chebyshev()` 現在**只**存在於 `core/los.ts`，用於半身掩體的 8 鄰域遮擋判定——
那是幾何判定的一部分，不是距離比較。任何距離比較都必須用 `manhattan()`。

兩個預期中的行為變化（正常，不是 bug）：

- 射程 8 的武器在正前方仍可打 8 格，斜 45 度方向只剩 4 格（實測比值 0.50）
- 會出現「看得見但打不到」的敵人：不給合法目標框，但仍然看得見

視野實測（士兵站在中央大廳 `(7,9)`）：站立可見 **95** 格；蹲下依面向落在 **22～50** 格
（北 24／東 35／南 50／西 22 —— 差異來自那個位置周圍的牆，不是規則有偏心）。
（v0.2 用切比雪夫時是 103 / 61；改用曼哈頓後可及範圍本來就會縮，遮擋規則本身沒變。）

## 命中管線

擲骰自 v0.5 起已啟用，但整條管線從 MVP 第一天就是活的：

- `toHitChance()` 委派給一個可切換的策略。`data/rules.json → combat.enableToHitRoll` 設成 `false`

## 行動排程器：沒有回合，也沒有 AP

v0.7 把 2 AP 制整個拆掉。`GameState` 裡沒有 `turn`、沒有 `phase`、沒有 `enemyQueue`；
`Unit` 裡沒有 `ap`／`maxAp`。取而代之的是一個 `clock` 和每個單位身上的 `nextActAt`。

主迴圈永遠是同一件事（`core/scheduler.ts`）：

```
挑出 nextActAt 最小的存活單位 → clock 推進到它 → 它做一個動作
                              → nextActAt = clock + 該動作的時間成本 → 重來
```

**一個動作 = 一次輪到你。** 走一格是一次，開一槍是一次。沒有 AP 可以攢，
也沒有「等這一輪結束」。同時刻的先後是三層決定性比較：時刻小的先 → 玩家先 → 陣列索引小的先。
玩家優先是刻意的：時間打平時把行動權給玩家，玩家才不會覺得被系統偷了一手。

### 為什麼值得換掉 AP

AP 制把「快」和「慢」壓成同一個節拍——不管衝鋒型多快，一輪就是一輪，
所以「比玩家快」得另外寫一條規則（給它 3 AP）。排程器讓速度變成一個真正的維度：

| | v0.6（AP） | v0.7（時間） |
|---|---|---|
| 衝鋒型比玩家快 | 特例：`ap: 3` | `moveTime: 7` vs 玩家 10，排程器自己會讓它多動 |
| 重武器很重 | 特例：`fireCost: 2` + 「等於結束回合」 | `fireTime: 20`，就是別人動兩次的時間 |
| 射手型不能連打 | 特例：`attacksPerTurn: 1` | `fireTime: 12`，比玩家一個動作稍慢，自然不會連打 |
| 剛發現不能開火 | 特例：`justSpotted` 旗標 | 轉換本身是個要花 `transitionTime` 的動作 |

四條特例規則變成四個資料欄位。**v0.7 完全沒有動平衡數值**——所有時間都是 v0.6 的 AP × 10。

> `attacksPerTurn` / `shotsThisTurn` 直接刪掉了：「每回合上限 1 次」在沒有回合之後
> 不對應任何東西。射手型的節奏改由 `fireTime: 12` 決定。

### 兩個必須守住的不變式

1. **零成本動作不讓出行動權**（姿勢、面向的時間成本是 0）。所以 **AI 絕對不能選 0 成本動作**，
   否則主迴圈原地無限迴圈。這條寫在 `rules.json` 的註解裡，也有測試釘著。
2. **畫面上不得洩漏行動順序。** 沒有時間軸、沒有「下一個是誰」、沒有敵人頭上的倒數。
   HUD 只顯示世界時刻 `T`。誰快誰慢要靠玩家自己觀察。

### 系列動作：走到一半是可以被打斷的

`core/sequence.ts`。某些動作太重，用一個大時間成本表現會讓單位在一段長時間裡「不存在」。
系列動作把它拆成數步：**時間照樣一步步花掉，但效果只在整套走完的那一刻發生**。

MVP 只有一個：RR-4 裝填拆成「開栓退殼 10 + 裝入彈藥 10」。總時間跟原本一樣是 20，
差別在中間那 10 個時間單位裡，你是可以被打斷的，而且**看得見自己正在蓄勢**——
橫幅寫「裝填 RR-4：開栓退殼（1/2）」，裝填鍵變成「續 10」，其餘動作鍵全部灰掉。

中止的入口在「點自己」的詳細狀態卡片裡，並明寫**已花費的時間不退還**。
單位死亡時序列連同單位一起消失，效果不發生——那把空的 RR-4 就躺在屍體上。

## 為什麼要把基礎命中降到 0.55

v0.5 做完掩蔽之後，基礎命中 0.85 減掉良好掩蔽 0.40 還有 45% ——
**掩體只是讓事情變慢，不會改變結果**，玩家沒有理由繞側翼。

v0.6 把基礎降到 0.55，同一個掩蔽把命中率壓到 15%（下限）。實測落差：

| 情境 | 命中率 |
|---|---|
| 開闊地站對站 | 55% |
| 目標蹲下 | 40% |
| 目標有部分掩蔽 | 30% |
| 目標有良好掩蔽 | **15%**（下限） |

配套是彈匣 6 → 4：命中率低但子彈免費的話，最優解會退化成站著一直開槍，
**煞車必須是彈藥**。四發在 55% 下平均命中 2.2 發。
「這一發值不值得」因此成為每次開槍都要問的問題 —— 剛好落在世界觀那句話上：子彈比人貴。

生命值同步下修（士兵 60、衝鋒 25、射手 30、裝甲 90），讓雙方都能被兩三發打死。
**衝鋒型 25 血，步槍命中一發必死**；**裝甲型 90 血對 RR-4 是一發賭命**（約 76% 機率一擊斃命，
但只有 50% 命中率）。

## 兩段式察覺：一段時間的反應窗口

敵人從 `IDLE` 看到你時，**那一次輪到它只做「轉入警戒」**，花掉自己的 `transitionTime`，
不開火也不移動。那段時間正是玩家用來蹲下、退回掩體或先開槍的窗口。

v0.7 之後這不再是一條特例規則，而是排程器的自然結果：轉換就是一個要花時間的動作。

關鍵是那條例外：**已在 `SEARCH` 的敵人重新取得視線可以立刻開火**。
少了它，玩家就能「開槍 → 退出視線 → 再進入視線 → 敵人又剛發現」無限騷擾。
要重新拿到窗口，得先躲滿整個 `searchTimer` 讓敵人真的放棄。

> **窗口是一段時間，不是保證的一個動作。** 衝鋒型的 `transitionTime` 只有 5，
> 而玩家一個動作是 10 —— 它可能在你動一次之前就轉換完成並打你一拳。
> 對付快的東西要靠先手，不是靠反應。

三種狀態在畫面上必須分得出來，否則這條規則等於不存在：

| 狀態 | 表現 |
|---|---|
| 剛發現（這次不開火） | **琥珀色虛線框 + 頭上「剛發現」** |
| 一般警戒 | 紅色閃爍實線框 + `!` |
| 搜索中 | 紅框 + `?` |

## 遮蔽 vs 掩蔽：兩個檢查，互不相干

v0.5 最容易搞混的一組概念，所以在程式碼裡也是兩個獨立模組：

| | 回答的問題 | 演算法 | 結果 | 檔案 |
|---|---|---|---|---|
| **遮蔽** | 看不看得見 | 幾何射線（對稱 Bresenham） | 二元 | `core/los.ts`（**一行都沒動**） |
| **掩蔽** | 好不好打中 | 目標鄰格掃描 | 三級 | `core/cover.ts`（新增） |

掩蔽刻意不走射線：現有模型裡射線通過 `WALL` 就直接阻擋，不存在「射線切到牆但仍看得見」的
中間狀態，所以要讓牆提供掩蔽，來源必須是另一個檢查。

掩蔽只看目標**朝向射手那一側**的正交鄰格（最多兩格），因此**射手繞個角度就能消除它** ——
側翼是掩蔽的解法，這是整個機制最重要的戰術產出。三級列舉而不是每格累加：
純疊加沒有上界，掩蔽加蹲姿加射程衰減會把命中率壓到下限、雙方互相打不中、時間空轉。

> 一個反直覺但正確的推論：**正交直線對射時通常沒有掩蔽**。目標朝向射手那一側的鄰格
> 若是阻擋物，那格必然在射線上，結果是遮蔽（完全看不見）而不是掩蔽。
> 走廊裡的正面對射因此非常致命 —— 這是設計意圖。
> 寫測試時我一開始就踩了這個坑：想找「有掩蔽又看得見」的組合，手挑的座標全部是遮蔽。
> 最後是寫一支腳本掃過整張地圖才找到 —— 那些組合都在**斜向**上。

蹲姿的完整代價見下一節：v0.8 把它從「看多遠」換成「看哪裡」。

## 面向：從美術欄位變成規則

`facing` 從第一版就留著，一直沒有啟用。v0.8 讓它生效，但**只在蹲下時**：

| 姿勢 | 視野方向 |
|---|---|
| 站立 | 全方位（面向不影響任何規則） |
| 蹲下 | **面向的前方半平面**，含垂直於面向的那條線 |

判定式就是一個內積：`(target − observer) · DIR_VEC[facing] >= 0`。

**為什麼是蹲下才生效**：本作沒有平移（strafe）手段。若面向隨時生效、轉向又要收費，
等於對所有移動課稅。限制在蹲姿時，面向只在單位大多靜止的狀態下起作用，移動完全不受影響。

**「含垂直線」不是為了好寫**，它自動長出正確的形狀——面向北時正東正西的相鄰格看得見，
後方三格是盲區。不含那條線的話，蹲下就看不到自己身旁兩格，蹲在牆邊會瞎得很莫名其妙。
反過來說，半平面本身已經夠了，不需要再補一條周邊視覺規則。

**敵人一律有盲區**，不管姿勢（它們永遠站著）。這是刻意的不對稱，記在「已知的難度偏移」。

視野實測（中央大廳 `(7,9)`）：站立 95 格，蹲下依面向 22～50 格。

### 蹲姿的代價換了一種

v0.5 用「蹲姿視野 ×0.6」當代價，v0.8 移除。它懲罰的是「看多遠」，
而面向懲罰的是「看哪裡」——後者才是要玩家做的決定。兩個疊在一起會把蹲姿削過頭。

取而代之的第二個代價是**姿勢改變花 3**（移動一格是 10）。這條非加不可：

> 若站起來免費，玩家的掃視流程會變成「站起來看一圈、蹲回去」——**免費取得全方位資訊**，
> 蹲姿的面向限制等於不存在，只多了兩次點擊。
> 通則是：**任何免費的動作，只要能解除資訊限制，它就是一次免費掃視。**

收 3 之後掃一圈要花 6，約半次移動。「要不要花這個代價確認周圍」因此成為真正的決定。

### 蹲姿的方向鍵：先轉向、再移動

蹲下時方向鍵若與當前面向不同，第一下**只轉向**（不移動、不花時間），再按一次才走。
防呆理由很直接：蹲姿的視野由面向決定，玩家想調整視野時最不該發生的事就是意外離開掩體。

轉向**永遠合法**，即使那個方向是牆——面向牆壁蹲著也是一種選擇。撞牆是在第二下才被擋。

同一顆鍵有兩種意思，所以按下去之前就要分得出來：會走的方向是實線青框，
會轉的方向是虛線琥珀框。

### 感知與轉向的先後不可以顛倒

敵人偵測用的是**這一次行動開始時**的面向，轉向是行動的附帶效果。
你只能轉向已經注意到的東西，不能先假設自己會轉對邊。

寫成「先朝玩家轉再看」的話，敵人永遠看得見玩家，整個面向系統等於不存在。
因為 `ALERT` 的敵人每次行動都盯著你，繞到它背後要走好幾步；而它一旦跟丟就轉入 `SEARCH`。
這正是面向想要的產出。

## 背刺：繞過去要有結算上的意義

攻擊一個**對你沒有視線**的目標時：命中率 **+0.30**，且**無視掩蔽**。

判定是 `!canSee(map, target, attacker.pos)`——用目標自己的視野規則反過來看你。
所以背刺有三種成立方式，都是同一條規則：

1. **繞到背後**（落在目標的面向盲區）
2. **目標被牆擋住看不到你**（遮蔽）
3. **你在目標的視野距離之外開槍**（射程）——狙擊本來就是背刺

第 3 點是自然推論而不是漏洞：`HULK` 視野只有 8，用射程 12 的 RR-4 從 10 格外打它，
它確實不知道你在哪裡。

**沒有這條規則的話**，「攻擊沒發現你的敵人」與「攻擊正在對射的敵人」在結算上完全相同，
繞到背後就只是「先開槍」，不成其為玩法。這條之後也會直接支撐潛入契約與消音武器。

規則**雙向生效**。由於玩家站立時是全方位視野，**玩家只有蹲下時才可能被背刺**。
而 `ALERT` 的敵人每次行動都面向你，所以**打不出背刺**——你不可能背刺一個正在對你開槍的人。

背刺成立時攻擊預覽整條標籤轉成琥珀色，寫「背刺 +30%・無視掩蔽」；
原本有掩蔽的目標會顯示「部分掩蔽 已失效」而不是把掩蔽藏起來——
玩家要看得出是自己繞背才讓它失效的。

## v0.9：四件互相咬合的事

彈藥、射擊模式、背包、搜刮是一起上的，因為**任何一件單獨做都不成立**：

- 射擊模式若沒有彈藥稀缺就不是決策——火力大的模式永遠划算
- 搜刮若沒有容量上限就不是決策——把地圖清空即可
- 戰利品若沒有撤離管道就沒有意義

### 彈藥只有兩層

**槍內剩餘子彈**與**背包內的總發數**。不追蹤彈匣個數、沒有上膛殘彈——那是模擬，不是決策。
裝填 = 從背包扣除差額，把槍補滿；背包不足就補多少算多少。

HUD 寫成 `AR-9 8/8｜備 24`。槍內剩幾發只是一半的資訊。

### 射擊模式：同樣的時間，不同的耗彈與準度

| 模式 | 耗彈 | 判定次數 | 命中修正 | 期望命中數（基礎 0.55） |
|---|---|---|---|---|
| 單發 | 1 | 1 | **+0.10** | 0.65 |
| 點放 | 2 | 2 | 0 | 1.10 |
| 連發 | 3 | 3 | **−0.10** | 1.35 |

**三種模式的時間花費完全相同。** 差別只在你燒掉幾發子彈。

**連發不是「一次判定但命中率較高」**，而是三次各自獨立的完整判定：各自擲命中、各自擲傷害、
各自擲護甲。所以它同時具備傷害上限（三發全中即三倍）與高變異——
「我需要它現在就死」因而成為一個真正的選項。

連發期望傷害最高但每發子彈效率最低；單發反過來。
**重甲目標非常吃彈藥**：每發淨傷從約 30 掉到約 11，同樣要打掉它得燒三倍的子彈——
這是換用重武器的另一個理由，與時間無關。

模式是**一顆獨立的按鈕**，不是每次開火都要選。射擊是全遊戲最高頻的動作，
不可以每發都停下來做一次選擇。點一下循環「單 → 點 → 連」，不花時間，**記在武器上**
（換到 RR-4 再換回來仍是先前的設定）。開火本身完全沒變，還是兩段式點擊。

彈藥不足時**自動降級**（連發→點放→單發），但**絕不無聲降級**：按鈕轉成虛線琥珀框，
攻擊預覽寫「（彈藥不足，已降級）」。玩家選的模式不變，補彈之後就回到原本的火力。

> **AR-9 彈匣 4 → 8 是被射擊模式逼出來的，不是平衡調整。**
> 連發一次吃 3 發，彈匣仍為 4 的話會有一半的行動花在裝填上。

### 背包：貪心被標了價

背包有 50 的重量上限，超過就撿不起來。負重同時決定移動時間：

| 負重 | 移動一格 |
|---|---|
| ≤ 20 | 10 |
| ≤ 35 | 12 |
| ≤ 50 | 14 |

初始負重是 **18**（24 發步槍彈 12 + 2 發火箭彈 6），刻意貼著第一級的上緣——
**玩家一開始就站在門檻上，撿東西才會是個決定**。

沒有負重代價的話，最優解就是把地圖搬空。有了它，背得越多走得越慢，走得越慢越容易死。

**背包 = 你死掉會留在戰場上的東西。** 屍體回收因此從「回去撿那把砲」變成
「回去撿我這一路搜刮的所有東西」——玩家越貪，回去的動機越強，風險也越大。

### 搜刮：三種來源，一個型別

己方屍體、敵人屍體、地圖搜刮點共用同一個 `LootPile` 與同一套兩段式點擊文法。
分成三個型別的話，搜刮面板要寫三份、拾取指令要開三條路——沒有理由。

v0.9 起**敵人死亡也留下屍體**（掉落表在 `actors.json`，每項依序各抽一次亂數）。
己方屍體含兩把槍、背包全部內容，以及**一份 DNA**——局外層還不存在，
帶出去的 DNA 只會列在結算畫面上。

> 搜刮機制與 DNA 回收是同一套東西。這一版等於在不碰局外層的前提下，
> 把局外層最重要那條迴路的地基蓋好。

### 撤離：系統不禁止，只標價

**任何時候**回到初始空投點都可以走，背包內的一切帶出。主目標沒完成就是 `ABORTED`
（合約失敗），**但戰利品照樣帶出**。

戰利品一旦存在，「我東西撿夠了、主目標太硬、我走了」就是一個自然會浮現的決策——
而那正是最初設計止損按鈕時想要的東西，現在它有了實質內容。
任務不是打開了就必須打完的副本，而是一個可以走人的工地。

**撤離與止損是兩件事**：撤離是走出去（東西帶回來），止損是不要了（戰場上的一切全部損失）。
兩者的 `result` 都是 `ABORTED`，所以結算標題要分得出來——
「撤離完成 — 合約失敗」vs「任務中止（止損）」。

### 一個笨機器人抓到的規則漏洞

難度探針跑起來不會結束了：`TAKE_ALL` 在背包塞滿時仍然合法，於是機器人每按一次
白花 10 時間卻什麼都沒拿到，永遠卡在同一格。

修法不是改機器人，是改規則：**一件都拿不動時「全部拿走」是非法的**，按鈕灰掉。
`loot.test.ts` 把這條釘住了。

## v0.10：敵人開始用同一套詞彙

到 v0.9 為止，戰術層有一整套詞彙，但**只有玩家會用**：

| 玩家會用 | 敵人會用 |
|---|---|
| 掩蔽、側翼繞行 | — |
| 蹲姿與面向、背刺 | — |
| 三種射擊模式 | — |
| 移動、射擊 | 移動、射擊 |

問題不是太簡單，是**數值已經無法判讀**——基礎命中 0.55、掩蔽減免最高 −0.40，
代表玩家躲好時是 15% 對 55%。從那裡開始的每一次調整都是對著壞掉的基準做的。

### 落點評分取代貪婪逼近

ALERT 時不再走最短路，而是對**四個正交鄰格 + 留在原地**評分後選最高：

| 項目 | 說明 |
|---|---|
| `approach` | 距離變化，接近 +1 |
| `selfCover` | 這一格相對於玩家的掩蔽 |
| `targetExposure` | **從這一格看過去，玩家的掩蔽**（越低越好） |
| `canShoot` | 從這一格打不打得到 |

`targetExposure` 是本次最重要的一項：它只是把既有的掩蔽函式**射手與目標對調**，
成本極低，但它讓敵人主動繞開玩家的掩體——側翼第一次被敵人使用。

**權重依原型不同**（`actors.json`），否則三種敵人會退化成同一種打法：
衝鋒型 `approach` 一面倒；射手型 `targetExposure`/`selfCover` 高；裝甲型緩慢推進。

**打得到就打，除非換一格能打得更好。** 敵人永遠不會為了躲而放棄射線——
只有當某個鄰格「也還打得到」且位置更好時才先換位。
這一步只比位置項、不含 `approach`：含了會震盪（`approach` 對相鄰兩格符號相反，
A 想去 B、到了 B 又想回 A），只比位置項則不可能來回。

### 兩個實作上的坑

**射手蹲進半身掩體會把自己弄瞎。** v0.8 的 §7.2 說緊鄰半身掩體蹲下是**雙向阻擋**——
所以「有掩蔽就蹲下」會讓射手蹲進去、看不見、轉入搜索、站起來、再蹲一次。
條件必須以**蹲下之後**是否還有視線為準。玩家在同一個位置也不會蹲，他會站著越過掩體開槍。

**宣告開火綁的是「開火」，不是「打那一格」。** 一開始寫成「目標必須待在同一格才有效」，
結果笨機器人幾乎每個動作都在走，敵人一槍都打不出來——那不是拘束力，那是把敵人關掉。
失效條件就是規格列的三件事：脫離視線、脫離射程、目標已死亡。

### 口令：說了就一定做

敵人行動時會喊出**下一個動作**，而且下次輪到它時**必定執行，不重新評估**。

> 玩家聽到「繞右邊」「開火」之後移動破壞它的射線，那一發就整個浪費掉。
> **打斷敵人已宣告的攻擊，等於讓它損失一整個行動。**

代價是 AI 依據稍舊的資訊行動——這是刻意的取捨：可被預測、可被玩弄的敵人，
比反應完美的敵人有趣得多。

口令**由決策理由碼產生，不是事後推測**。否則調完權重之後口令就會開始說謊。
順帶它是很好的除錯工具：調權重時可以直接從口令看出每隻敵人為什麼那樣走。

聽覺有距離（曼哈頓 12）但**牆壁不擋**，與噪音機制一致。
**可聽與否的判定在規則層**——聽不到就根本不發事件，不能丟給渲染層決定。

`IDLE` 的敵人**不喊**。這保護了偷襲與將來的潛入契約，
也讓「什麼時候變得吵起來」本身成為一個訊號。

看得見的敵人把口令畫在頭上；只聽得到的**只報方位**（「東北方：繞右邊」），
不報座標——否則面向視野系統會被架空。

### IDLE 會轉頭了

IDLE 敵人在「原地警戒」與「轉 90 度」之間交替，固定周期、固定方向。

- **要花時間**：轉向本身是 0 成本，而 AI 不得選 0 成本動作（會無限迴圈），
  所以巡視是一個獨立的、有花費的動作
- **要可預測**：玩家可以觀察、計時、抓空檔。**盲區從白拿變成需要時機的解謎**

SEARCH 抵達最後已知位置後會先站定、再巡視兩次才放棄——噪音引誘因此更有價值。

## v0.12：恢復必須慢、必須不完全、必須稀有

實測顯示開闊地圖的正確打法是脫離接觸、蹲下、找掩護、逐一孤立敵人。
既然**在火力下移動、承受傷害後退出交火**是會反覆出現的正常情境，
就需要一個把傷害轉回可用狀態的手段。

但恢復會直接衝擊本作的核心結構——士兵是消耗品、死亡是支出而非失敗、
屍體回收是最重要的單一決策。**如果恢復又快又便宜，這三件事會同時失去意義。**

| 約束 | 作法 |
|---|---|
| **慢** | 40 時間（＝四次移動），做成系列動作，中途被打斷即失敗 |
| **不完全** | 25 HP，士兵滿血 60，永遠回不滿 |
| **稀有** | 不是標準配備，初始只有一個，其餘靠搜刮 |

**慢是最重要的一條**：它讓恢復無法在交火中進行。玩家必須先脫離接觸——
而那正好就是這一版想支援的那個打法。

### 系列動作現在分兩種

| 類型 | 中斷後 | 適用 |
|---|---|---|
| **可續行** `RESUMABLE` | 進度保留，下次從中斷處接續 | 機械性動作（重武器裝填） |
| **須重來** `RESTART` | 進度歸零，時間不退還 | 生理性動作（治療） |

判準是**已經完成的物理狀態改變會不會自己消失**：
退殼退了就是退了，不會自己裝回去；包紮包到一半被打斷，那塊敷料就廢了。

**可續行的進度存在物件上，不是存在單位上**——`Weapon.reloadProgress`。
所以收起武器、換另一把、之後再換回來，進度仍在；而已退殼未裝填的槍**不可使用**。

這產生一個很好的戰術狀態：**你開始裝填、挨了一輪、退回掩體、接著裝完。**
總時間沒變，改變的只是投入的時間不會因為被打斷而白費。

### 背包裡沒有「使用」，只有「準備」

物品從背包選取後進**準備欄**，回到戰鬥主畫面才用「用」鍵執行。準備欄只有一格。

**準備要花 10。** 免費的話準備欄就只是多一次點擊——玩家會在需要時免費換上
想要的東西，等同於直接從背包使用。收 10 之後它與「現在手上拿的是哪把槍」
完全對稱：**你身上現在準備好的是什麼，是一個要提前做、事後才發現對不對的決定。**

反過來，**丟棄免費**。丟東西比撿東西快，而且緊急時減重不該被時間懲罰——
負重直接等於被追擊時的生存率。

### 負重終於裝上了煞車

v0.9 給了負重代價卻沒給釋放閥：整個指令表裡**沒有丟棄**，
背包唯一會變輕的路徑是裝填時扣彈藥。撿了就再也放不下。

現在丟棄的東西落在腳下成為可搜刮的堆，撿得回來。
背包介面也把負重級距說出來了（v0.9 起它是隱形的，玩家只能從移動變慢間接感覺到）：
`負重 23/50・移動 12`，外加「再撿 12.5 就會掉到下一級」。

## 負重的第一級放寬到 30

封合劑（重 5）變成強制攜帶之後，初始負重從 18 變成 **23**——原本會直接越過
第一級的門檻 20，等於把基準移動速度從 10 悄悄改成 12。那不是新增一個道具
該有的副作用：所有既有數值的基準都會跟著移動，SHOOTER（10）會變得比玩家快。

所以第一級從 20 放寬到 **30**：

| | 上限 | 移動一格 |
|---|---|---|
| 第一級 | 30 | 10 |
| 第二級 | 40 | 12 |
| 第三級 | 50 | 14 |

初始配備 23 仍然落在基準速度內，但**只剩 7 的餘裕**——撿一個動力核心（6）
就快要掉級了。「撿東西要付代價」還在，只是不會一撿就掉。

## v0.17：讓移動看得見，但不准擋路

v0.16 之後每一場都有後果了，但畫面上仍然是「單位瞬間換格」——
玩家看不到動作的開始，只看得到結果。那正是 v0.4 建立回饋層時要解決的同一個問題。

**這一版 `core/` 的 diff 是空的。**旋鈕也不放 `rules.json`，而是 `data/ui.json` ——
規則層對「攝影機平移要花幾毫秒」沒有意見，也不能有意見。

### 第一條規則不是「怎麼播」，是「怎麼被打斷」

> **動畫播放中收到新的輸入 → 當前這一步立刻瞬移完成 → 立即開始處理下一步。**

這是移動動畫毀掉 roguelike 手感最常見的方式：玩家連按方向鍵趕路時，
若每一步都要等動畫跑完，操作會變得非常黏。
**慢慢走的時候有演出，趕路的時候不擋人。**

實作上，`dispatch()` 的第一行就是 `motion.finishAll()`。
有一條驗收把動畫調到 2000ms 再連走四步：**四步花了 5ms**。

### 攝影機只在必要時才平移

跟隨當前行動中的單位，不分敵我 —— 但**目標已經舒服地待在畫面內時，不平移也不等待**。

這一條與「平移期間目標暫停行動」是一組的。若每一隻敵人都要「平移過去 → 等待 → 行動」，
十隻敵人的一輪會非常久，而大部分情況下目標本來就在畫面內。

實作時撞到一個必須補的例外：**地圖邊界會夾住鏡頭**。
目標卡在角落時，它「離畫面邊緣很近」是必然的，平移過去也不會改善 ——
所以判準補了一句「**平移不會真的移動視野時就不要平移**」，
否則整場都在為了角落的敵人多等一次 `panMs`。

### 動畫成本實測（§5 要求的量測）

同一張圖、同一個種子、同一套政策，只有旋鈕不同 ——
三次跑出來的**遊戲結果完全相同**（時刻 1659、陣亡 3、SUCCESS），差的只有牆鐘時間：

| 旋鈕 | 真實耗時 | 對照 |
|---|---|---|
| 全部 0（等同 v0.16） | 64.9 秒 | 基準 |
| **預設**（玩家 80／敵人 180／平移 220） | **67.9 秒** | **+2.9 秒** |
| 刻意調慢（玩家 300／敵人 500／平移 600） | 103.0 秒 | +38.0 秒 |

**預設值幾乎不花錢，而原因值得寫下來**：動畫長度**塞得進既有的節奏間隔裡**
（`playerMoveStepMs` 110 > 80、`enemyStepMs` 200 > 180），所以它們只是把原本的空檔填滿。
真正會加時間的只有攝影機平移的等待。

所以風險線很明確：**把 `enemyMoveMs` 調過 200、或 `playerMoveMs` 調過 110，
就會開始真的變慢** —— 調慢那一組就是踩過去之後的樣子。
v0.13 收斂出來的 15～25 分鐘沒有被推出去。

（`scripts/pace.mjs` 量畫面，`scripts/botrun.ts` 量規則。兩支是兩回事。）

### 選單通則

> **凡是不消耗遊戲時間的介面，都可以蓋住整張地圖。**
> **凡是會消耗遊戲時間的操作，必須保持地圖可見。**

判準很乾淨：不花時間就代表**盤面是靜止的**，玩家不需要一邊看地圖一邊決策。
背包、掠奪、日誌、士兵資訊現在全部滿版；射擊與移動預覽本來就畫在戰場上，不受影響。

掠奪選單改用兩個明確的關閉條件（容器被掠奪後不會消失，所以不能用「主體失效」）：
**拿空了**，或**走離相鄰範圍**。

### 順手修掉的一個舊 bug

`spotlight`（鏡頭聚焦在正在行動的敵人）只在敵人回合結束時清除。
如果輪到玩家時它還留著，鏡頭會卡在上一個行動者那裡。
以前看不出來是因為鏡頭本來就是瞬間跳的；加上平移之後它會變成一次沒有理由的滑動。

## v0.16：把電接上去

**專案至此蓋好的核心機制，在這一版之前全部沒有作用。**

| 已實作的機制 | v0.15 為止的實際後果 |
|---|---|
| 陣亡掉落武器、遺落即失去 | 無 —— 下一場全部回來 |
| 屍體回收 | 無 |
| 帶著戰利品提早撤離 | 無 |
| 止損按鈕 | 無 |
| 名冊耗盡 | 重開就好 |
| 搜刮與結算清單 | 顯示完就丟掉 |
| 配裝取捨 | 沒有稀缺性，只是「哪個比較強」 |

**「要不要冒險走回去撿自己的屍體」是本作的核心決策，而它到目前為止一次都沒有真正發生過。**
玩家回去撿，得到的是一個結算畫面上的數字，然後那個數字被丟掉。

### 分層：任務仍然是純函數

`MetaState` 不進 `GameState`。任務開始時取一份**派遣快照**，
任務期間完全不讀寫局外層 —— 連替補都是從快照裡取 —— 結束後才把結果套回去。

```
mission(派遣快照, 種子, 玩家輸入) → 任務結果
```

四條硬性要求一條都沒動。順帶一提，附錄 A 那個「`instanceId` 必須來自決定性來源」
的要求在這一版才真正兌現：**那個計數器要跟著存檔一起持久化**，
否則重新載入頁面之後會發出重複的識別碼，武器追蹤會從根部壞掉。

### 配裝從「選裝備」變成「分配資源」

- **武器是實例，同一把槍只能給一個人。**三把槍四個人，就有一個人沒槍。
- **彈藥與消耗品是共用庫存，逐人分配。**60 發 5.56 和三個人，你要決定怎麼分。

新公司刻意給四個人、四把槍 —— **第一次進入配裝畫面就會遇到「東西不夠分」**。

由此自然長出兩種原型，兩種都不需要額外設計：

| 原型 | 內容 |
|---|---|
| **主攻** | 重裝、彈藥充足、載重量吃緊 |
| **回收** | 只帶手槍與封合劑，**刻意把載重量留空**，去把前一個人的東西撿回來 |

第二種完全是規則自己長出來的。有一條測試在守它成立：
主攻約 46 重、回收 2.7 重，兩者的載重餘裕差 40 以上 —— 那個差距就是他背得回來的東西。

### 止損現在要付代價

撤離與止損以前的差別只在結算畫面的標題。現在：

> **止損 = 人回來，身上與背包的一切留在戰場上。**

如果止損不必付代價，它就會**嚴格優於**走到撤離點 —— 而那一段路正是本作的張力所在。

### 替補帶著自己的配裝

v0.15 以前替補一律「配發一把 AR-9」。現在他帶著公司畫面上分給他的東西降落，
**沒有配裝的人就赤手空拳落地** —— 那是玩家的責任，遊戲不擋。

### 機器人基準因此變了，而且是應該變

| 地圖 | v0.15 | v0.16 |
|---|---|---|
| 廢棄水處理廠 | 5/5　陣亡 1.2 | 5/5　陣亡 1.2 |
| 輸送管廊 | 5/5　陣亡 1.4 | **4/5**　陣亡 1.8 |
| 乾涸沉澱池 | 2/5　陣亡 3.4 | **4/5**　陣亡 2.8 |
| 舊倉儲區 | 5/5　陣亡 0.8 | 5/5　陣亡 1.0 |

原因是替補規則改了：機器人用的測試快照給每個人 AR-9 + RR-4，
所以替補比以前（只有 AR-9、沒有火箭彈）**強得多**。開闊圖因此變好打。
這不是回歸失敗，是 §4.2 要求的規則變更的直接後果。

**真人玩家不會有這個待遇** —— 他的替補帶的是他自己分得出來的東西，而東西是有限的。

### 補給站是明確的佔位

全部 0 元，畫面上就寫著「暫時性的測試機能」。做成商店的形狀而不是一顆「新增」按鈕，
是為了讓經濟層之後只需要填入價格，不必重做介面。
它的最終形態是**合成（長士兵、做土製槍）＋交易（取得遺產武器）**。

### 存檔不做遷移

`schemaVersion` 不符就提示「重置並開始新公司」。專案迭代很快，
格式會被之後每一版打破，而**遷移程式碼的維護成本遠高於重來一次**。
公司畫面底部有重置入口（按兩次確認），也支援 `?reset=1`。

## v0.15：把 v0.14 做完

v0.14 的合約清單會告訴玩家「開闊地形、敵方以遠程為主、存在重裝目標」——
**然後玩家什麼都不能改變**。有標籤而沒有配裝，比沒有標籤更糟。
這一版補上那一段：**標籤 → 準備 → 出擊**。

**AR-9 與 RR-4 的數值一個字都沒動。**它們是花了六個版本調出來的參考點，
重設計會讓所有既有的手感判斷失效。

### 角色分化靠衰減曲線，不靠傷害數字

`optimalRange` 與 `falloffPerTile` 從 v0.5 就存在，卻幾乎沒被用到。
這批新武器把全部的分化壓在它們身上（下列為武器基礎命中，不含單發模式的 +0.10）：

| | 1 格 | 2 格 | 3 格 | 5 格 | 14 格 | 16 格 |
|---|---|---|---|---|---|---|
| SG-12S 削短霰彈槍 | **0.80** | 0.50 | 0.20 | 打不到 | | |
| SG-12P 泵動霰彈槍 | 0.70 | 0.70 | 0.50 | 觸底 | | |
| P-9 手槍 | 0.60 | 0.60 | 0.60 | 0.36 | | |
| DMR-7 精確射手步槍 | 0.50 | 0.50 | 0.50 | 0.50 | **0.50** | 0.40 |

DMR-7 的基礎命中比 AR-9 還低。**它的長處不是準，是遠處也一樣準。**

散佈刻意**不**用多發判定表現 —— 衰減曲線已經在做距離衰減，
再疊一層等於雙重衰減，而且變異來源疊了兩個。
多發判定留給射擊模式專用，兩個機制維持正交。

### 兩把霰彈槍性格對立，而不只是數值不同

泵動型是**增量裝填**：一次填一發、每發 6，但在任何一發之後都可以直接開槍。
削短型是它的反面：一次填兩發、單一動作、費時 20。**零承諾 vs 高承諾。**

> 增量裝填**不是**系列動作，不用 `RESUMABLE` 實作。每一發都是一個完整結束的動作，
> 沒有進度要保存，也沒有承諾可以被打斷。手感就是這樣長出來的：
> 壓力下填一發打一發，安全時才填滿。

削短型另外有**齊射**：吃 2 發、2 次獨立判定，數值與點放相同。
差別在意圖 —— 連發是「用彈藥換命中機會」，齊射是「梭哈把它打死，還是留一發」，
因為它的彈倉只有 2 發，齊射等於清空。

### 重量從此有換算尺

> **1 遊戲重量單位 = 0.5 公斤。**

以前的重量是隨手填的（封合劑 5、步槍彈 0.5）。現在全部由現實裝備換算：
M4A1 3.4 kg → 7，Carl Gustaf 10 kg → 20，Glock 17 1 kg → 2。
**之後新增任何物品都依此換算，不再臨時決定數字。**

同時**手持與收納的武器開始計入負重**。以前不計，於是「多帶一把槍」是完全免費的——
那樣的話配裝畫面就沒有取捨可言，只剩「全都帶」。門檻依此重設為 55／78／100。

實算各種組合（預設配裝 41.6，餘裕 13.4）：

| 組合 | 總重 | 級距 |
|---|---|---|
| SG-12S + P-9（12ga×12、9mm×30） | 10.8 | 基準 |
| SG-12P + AR-9（12ga×20、5.56×32） | 18.6 | 基準 |
| SG-12S + DMR-7（12ga×12、7.62×20） | 20.0 | 基準 |
| **AR-9 + RR-4（預設）** | **41.6** | 基準 |
| LMG-5 + RR-4（5.56×60、84mm×2） | 50.4 | 基準（剩 4.6） |

### 彈藥的重量幾乎不重要，這是物理事實不是設計失誤

24 發 5.56 只有 0.58 單位。現實中要背到有感得帶數百發。
真正咬人的只有 84mm —— 每發 6，帶兩發就是 12。

所以配裝的實際決策不是「餵幾種彈藥」的重量，而是：
**我要在開始搜刮之前，先花掉多少載重量？**
帶 RR-4 加兩發火箭就佔掉 32；帶 SG-12S 加 P-9 只佔 7，留下大量空間給戰利品。

> 若日後希望彈藥數量本身成為約束，正確作法**不是**加重彈藥（那會違背現實比例），
> 而是加入每口徑的攜行槽位上限，也就是彈袋數量。本次不做，記錄備查。

### 附錄 A：一把槍是一個實例，不是一個型號引用

這一段完全不改玩法，只把資料模型改成日後接得上的形狀。

長期路線是：武器會有詞條而變得獨一無二，並且在伺服器端流通 ——
玩家陣亡遺落的槍，經拾荒者回收後重新洗進獎勵池，可能出現在另一個玩家的任務裡。
**那條路線的最低前提就是這件事。**若武器只是「玩家擁有 AR-9 這個型號」，
就沒有任何東西可以被追蹤、被標記、被賦予來歷 —— 追蹤到的只是一個名字。

現在加欄位幾乎零成本；等背包、屍體、戰利品、配裝、存檔全部長好之後再改，
會動到每一處。這與命中率鉤子、`penetration` 欄位、`CombatEvent` 事件流
是同一種作法：**先留形狀、後填內容。**

`affixes` 與 `provenance` 一律為空，但有效數值的計算**確實會走套用點**
（`基礎型號數值 → 套用詞條 → 實際數值`）。有一條測試專門守
「詞條為空時實際數值等於型號數值」—— 這樣日後真的填入詞條時，
就知道套用點在生效而不是被繞過去了。

`instanceId` 走的是與物品、屍體同一個流水號，因為它必須是決定性的：
若識別碼用時間戳或 UUID，「相同種子 + 相同指令序列 ⇒ 相同結果」這條就破了。

設定上的依據寫進了 [`docs/setting-bible.md`](docs/setting-bible.md)：

> **精密製造隨企業撤走了。這顆星球上的每一把槍，都是撤離之前製造的。**

槍不會被生產，只會流通。稀有度因此自我解釋 ——
好槍稀有不是因為掉落率，是因為世界上就剩那幾把。
被摧毀的槍永遠沒了，總數在**世界層級**緩慢減少，這比人為的耐久度更符合調性。
由此得到一條給經濟層的硬性約束（記在 [`docs/game-design.md`](docs/game-design.md)）：
**玩家永遠不能製造武器。合成可以長士兵，不能長槍 —— 人可以再長，槍不行。**

### 附錄 B：更正一句寫過頭的設定，順便把彈藥多包一層

附錄 A 寫下「這顆星球上的每一把槍都是撤離之前製造的，總數固定且只會減少」。
**那句話推論過頭了** —— 若所有槍都不可補充，這顆星球上早該沒有槍了，
但設定上到處都是武裝勢力。正確的版本是**撤離帶走的是精密製造，不是一切製造**：

| | 遺產武器 | 土製武器 |
|---|---|---|
| 來源 | 撤離前製造 | 現在仍可生產 |
| 補充 | **不可能** | 可以 |
| 經濟性質 | 不可替代的資本 | 消耗品 |
| 現有對應 | AR-9、DMR-7、LMG-5、RR-4 | 拉栓手槍與步槍、削短霰彈槍等 |

經濟層那條約束也跟著改寫，而且改完更硬：
**能製造的東西不保值；保值的東西不能製造。**
你當然可以焊一把管子霰彈槍，但沒有人會為它付錢。

彈藥同樣分兩層 —— **84mm 屬遺產彈藥**，RR-4 因此是一個會耗盡的資產：
每開一砲，世界上就永遠少一發。本版不為此加任何機制。

更正**不影響附錄 A 的任何一條**。實例、決定性識別碼、詞條套用點的理由全部成立，
而且在兩層版本下更成立 —— 需要被追蹤的正是那些不可補充的遺產武器。

**彈藥的識別單位改成「型別」，型別引用口徑。** 未來同一種口徑會有多種彈種
（12 號徑的鋼珠／獨頭／鋼索切段、5.56 的穿甲彈），而如果背包彈藥是
「口徑 → 數量」，日後背包、配裝、裝填、搜刮、屍體、結算清單每一處都要改。
與附錄 A 是同一類問題：現在多一層間接幾乎零成本。

武器也加了 `action`（`BREAK` / `PUMP` / `BOLT` / `SEMI` / `AUTO` / `BREECH`），
本版不參與任何判斷。它是為了這條規則預留的：

> 彈藥的相容性不只看口徑，還要看機構。破爛的中折式沒有複雜機構可以被打壞，
> 所以能塞任何東西進去；泵動槍的抽殼機構會被鋼索切段毀掉。

於是**最爛的槍會有最寬的彈藥相容性** —— 那是土製武器存在的意義：
讓粗糙成為一種能力，而不只是比較爛。

本版每個口徑只有一種彈種，數值一個字沒改，機器人數據逐位元相同。
介面上，一個口徑只有一種彈種時顯示口徑名（與以前完全一樣），
有多種時才把彈種名接上去 —— 玩家不必為了還不存在的東西多讀一行字。

### 機器人回歸：五個種子不夠

改動之後跑既有的五個種子，mission_03 從 4/5 掉到 2/5，看起來像是負重校準做壞了。
**不是。**逐項回退測出來的結果是：只要退回任何一組數值它就恢復，
但退回的組合彼此矛盾 —— 那是混沌，不是系統性偏移。

換二十個種子，兩版並排：

| 地圖 | v0.14（20 seeds） | v0.15（20 seeds） |
|---|---|---|
| 廢棄水處理廠 | 14/20　陣亡 1.5　時刻 1695 | 14/20　陣亡 1.4　時刻 1644 |
| 輸送管廊 | 20/20　陣亡 1.6　時刻 1820 | 20/20　陣亡 1.5　時刻 1628 |
| 乾涸沉澱池 | 16/20　陣亡 1.9　時刻 1683 | 17/20　陣亡 1.6　時刻 1584 |
| 舊倉儲區 | 20/20　陣亡 1.2　時刻 1814 | 19/20　陣亡 1.4　時刻 1621 |

沒有系統性偏移。順帶發現**那五個固定種子本身就是幸運樣本**：
mission_01 在五個種子上一直是 5/5，二十個種子只有 14/20。
`scripts/botrun.ts` 現在吃 `SEEDS=` 環境變數，判斷回歸時請用大樣本。

## v0.14：合約清單，以及「標籤不能手寫」這一條

局外層的第一塊。**刻意不含持久化與經濟** —— 沒有存檔，也不顯示任何報酬金額
（沒有貨幣系統，顯示金額等於說謊）。這一版只做一件事：把「打哪張圖」變成一個決策。

v0.11 起隨機選圖，玩家會**毫無預警**被丟進性格差異極大的地圖。
但「接哪張合約」要成為決策，玩家得先拿得到資訊 —— 而資訊必須可信。

### 這一版真正的規則只有一條

> **地形標籤與難度評級由地圖統計值推導，不得手寫。**

手寫的標籤會在地圖被修改之後開始說謊，而地圖一定會被修改 ——
v0.13 才剛把 mission_02 與 mission_03 整張換掉。如果那時候標籤是手寫的，
現在清單上就會有兩份在說前一版地圖的事，而且沒有任何機制會發現。

統計值不會。它跟著 `npm run map:build` 一起重算，CI 會比對 JSON 有沒有跟著更新。
改地圖 → 跑 build → 標籤自動變 —— 這條鏈上沒有人需要記得去改文案。

為此加了一個統計值 `openness`（開闊度）：可通行格周圍八格中**不是牆**的比例。
它刻意**不把半掩體算成阻擋**，因為它量的是建築的寬窄，而不是掩體多寡（那是
`coverDensity` 的事）。若把掩體一起算進去，掩體密集的倉儲區會被判成「狹窄」——
而那正好是它最不狹窄的原因。

### 四張圖推導出來的結果

| 地圖 | 評級 | 分數 | 自動產生的標籤 |
|---|---|---|---|
| 廢棄水處理廠 | **C** 例行 | 5.07 | 掩蔽充足、縱深大、存在重裝目標 |
| 舊倉儲區 | **B** 有阻力 | 7.18 | 掩蔽充足、開闊地形、存在無掩護路段、存在重裝目標 |
| 輸送管廊 | **A** 高風險 | 9.96 | 掩蔽稀少、空間狹窄、現地補給稀少、存在重裝目標 |
| 乾涸沉澱池 | **S** 資產減損預期偏高 | 10.87 | 敵方以遠程為主、開闊地形、存在無掩護路段、現地補給稀少 |

四張圖剛好各落一級 —— 這是門檻調出來的結果，不是巧合：
**全部擠在同一級就等於沒有評級。**

### 評級跟機器人的結果對不起來，而這是對的

輸送管廊評到 A，但機器人在那張圖上 5/5 全通、平均只死 1.4 個。
看起來像公式錯了。它沒錯 —— 它讀的是**地形說了什麼**：那張圖的掩體密度只有 4%，
是四張裡最裸的一張。而它之所以好打，是因為走廊窄到雙方多半根本看不到對方。

評級照實反映前者，因為那是玩家**在接合約的當下唯一能知道的東西**。
委託方不會附一份實測報告。如果讓公式去逼近機器人的結果，那就變成了
「用玩家還不知道的資訊去標示風險」—— 那不是評級，那是劇透。

（`openness` 有進公式，權重 8，所以狹窄確實把分數拉低了一點。
但它拉不動掩體密度那一項 —— 這是刻意的取捨，權重全在 `contract-rules.json`，
試玩後想改隨時可以改。）

### 簡報是手寫的，而且委託方沒有義務說實話

標籤與評級不能手寫，簡報則相反 —— **那是本作的敘事載體**。
主線與所有角色感都由合約簡報、公文與服役紀錄承擔，不做過場動畫。

文體規範只有一句：**用最無趣的公文語言，講最荒謬的事。不要吐槽，不要眨眼。**
會計與稽核語言優先，人命一律以財產語彙表達，公文格式要正確（旨／說明／辦法／附件），
**絕不解釋笑點**。

> 三、盤點時如遇非本部門編制之活動個體，視為盤盈，得依現況處理，
> 　　處理後於盤點表備註欄註記即可。

這種對比是設計的一部分：**卡片上半部的數字不會騙你，下半部的公文會。**

## v0.10 的實測結果與預期不同（這件事本身最重要）

`scripts/botrun.ts` 現在會在開關關閉與開啟兩種狀態下各跑一次。同一支笨機器人、同五個種子：

| | 成功 | 平均陣亡 | 平均耗彈 | 平均耗時 |
|---|---|---|---|---|
| `tacticalBehaviour` 關（= v0.9） | 5/5 | 2.4 | 34.6 | 1925 |
| `tacticalBehaviour` 開（= v0.10） | 5/5 | 2.2 | 33.0 | **2048** |

**幾乎沒有差別。** 只有總耗時上升 6%。

原因量得出來：**mission_01 上根本沒有掩體可用。**

- 十個敵人裡有**九個**，起始位置的四個鄰格加自己都沒有任何掩蔽
- 全圖 509 個可通行格中，對**東西向**射手提供掩蔽的只有 **14%**，對南北向的有 **28%**

規格 §13.1 要求半身掩體「成排配置」形成連續蹲行推進的路線——那些排是**水平**的，
提供的是對南北向射手的掩蔽；而這張地圖的動線是**東西向**（起點在西北角，終端在東南角）。

也就是說：AI 照規格實作了，一格前瞻的落點評分也運作正常
（`tactics.test.ts` 在有掩體的地形上驗得到繞側翼、蹲下、不繞路的衝鋒型），
但**這張地圖的幾何讓它幾乎沒有東西可用**。

這正是「多樣化地圖是下一版」的理由：現有的所有數值都是在同一組幾何上調出來的，
而 AI 的掩體運用也需要多樣地形才測得出來。

> 順帶一提，這支機器人只會單發、不會用掩體、不會繞背、不會利用口令，
> 所以它的勝率是**下界**。真人玩家的體感變化可能比這張表大。

## 戰場回饋層：不開日誌也看得懂

規則層每次套用指令會吐出一份**決定性的事件清單**，渲染層拿它播動畫：

```ts
applyCommand(state, cmd) => { state: GameState; events: CombatEvent[] }
```

事件有 `SHOT`／`IMPACT`／`MISS`／`KILL`／`NOISE`／`AI_STATE`／`AMMO_OUT`／`RELOAD`／`OBJECTIVE`／`DEPLOY`。
它們是純資料、可序列化、完全由狀態轉換推導而來，所以完全決定性。
**動畫的時間軸與播放狀態只活在 `render/effects.ts`，不進 `GameState`**，
回饋層也只是每幀被畫出來 —— 不阻塞輸入、不延後 `clock` 推進。

### 三種結果必須分得出來

這一條的優先度高於回饋層的其他所有項目：

| 結果 | 玩家該讀到的意思 | 判準 | 畫面 |
|---|---|---|---|
| 未命中 | 運氣不好，再開一槍 | 沒有 `IMPACT` | 虛線偏移彈道 + 灰色「未命中」 |
| **命中但被擋下大半** | **這把槍沒用，該換武器了** | `blocked >= amount` | 暗藍小號數字 + 青色「擋下 20」 |
| 命中 | 有效 | `blocked < amount` | 亮琥珀大號數字 |

裝甲型敵人在設計上的唯一任務，就是教會玩家「該換重武器了」。
如果玩家分不出「我沒打中」和「我打中了但沒用」，這個教學就不會發生，
裝甲型只會被當成一個很煩的高血量敵人。

而且教學在**開槍之前**就成立：鎖定裝甲型時標籤直接寫 `傷害 10–10　裝甲 20`。

> 標籤畫在目標**下方**，因為浮動數字一律往上飄 —— 一開始兩者疊在一起看不清，
> 分到上下兩側才解決。連續受擊的數字錯開時，每一階要拉開「主數字 + 副標」的**總高**，
> 只錯開半個字高一樣會咬在一起。

`effects.test.ts` 用一個假的 2D context 記錄實際畫出來的文字、顏色與字級，
確認三者顏色互不相同、被擋下的字比有效命中小、未命中真的會播、
連續受擊的間距大於一個字高、每個字都有描邊。

## 操作：一條文法，沒有例外

> **第一下：選取，並顯示「如果執行會發生什麼」。第二下：執行。**

兩條不變式讓這條文法成立：**選取永遠不消耗任何資源**（所以點錯無害，不需要「取消」鍵），
**選取狀態是持續且可見的**（所以不需要遮蔽戰場的彈出面板）。

| 目標 | 第一下 | 第二下 |
|---|---|---|
| 敵人 | 雷射瞄準線、紅點準星、名稱與命中率 | 開火 |
| 遠處空格 | 四方向路徑與所需總時間 | 沿路徑移動 |
| 屍體／搜刮點 | 可拿的東西清單（含「全部拿走」） | 全部拿走 |
| 相鄰的終端／補給箱／撤離點 | 互動內容與時間花費 | 執行 |
| 自己 | 詳細狀態 | —（一下就好） |
| 非法目標 | 無反應 | — |

**沒有開火按鈕。** 射擊一律透過地圖點擊，鎖定會一直保留：目標還活著、還在視線與射程內，
下次輪到你時第一下點它就是開火。

**唯一保留的確認彈窗**是「濺射會波及自己」。重武器開火要花 20（等於別人動兩次）也不另外確認——
兩段式點擊本身已經夠了。

### 目標框：兩種訊息，兩種表現

- **靜態細框** = 這個目標我現在打得到（視線、射程、彈藥皆成立）
- **點滅紅框** = 這個敵人不是 IDLE（ALERT 或 SEARCH）

兩者可以同時出現在同一個敵人身上。**框只表達狀態，不決定可否點擊**——
IDLE 的敵人一定要選得到、打得到，偷襲是核心玩法。

附帶效益：警戒狀態畫在敵人身上，噪音機制就從隱形變成可見的因果，
玩家看得出「我剛剛那一槍驚動了誰」。

### HUD 只放「這一下要做什麼」的輸入

判準只有一條：**這個數字會改變我這個動作的選擇嗎？**

| 常駐（兩列） | 為什麼 |
|---|---|
| `HP 60/60` | 還能挨幾發 |
| `AR-9 8/8｜備 24` | 還能開幾槍、要不要裝填 |
| `站・無人瞄準` / `蹲・部分掩蔽・2 人瞄得到` | 讓出行動權後會被怎麼打 |
| `負重 18/50`（被拖慢時追加 `・移動 12`） | 走一格要多久、還能撿多少 |

世界時刻、名冊剩餘、場上敵數、戰況損益**全部搬進日誌面板**。它們回答的是
「這一場打得怎麼樣」，不是「這一下要做什麼」——在直向手機上它們曾經吃掉將近
三成的畫面高度，而玩家並不會每個動作都去讀。搬進去之後離決策只差一個點擊，
止損的二次確認本來也會把同一份損益再顯示一次。

兩個常駐格還做了壓縮，省的不是字而是**不可用的資訊**：

- 沒人瞄得到你的時候，掩蔽等級不是可用的資訊——那時只顯示姿勢
- 沒被負重拖慢的時候，移動時間就是基準值——不用一直報

實測 HUD 高度：**64px**（390px 寬），約佔可視高度一成。

> 順手抓到一個更嚴重的 bug：小卡的 `max-height` 原本寫 `50dvh - 方向盤高 - 留白`。
> 在 844px 高的模擬器上是 172px，在真實手機（扣掉網址列後約 550px）只剩 **26px**——
> 日誌與搜刮面板在手機上等於塌掉。改成從實測的可觸區域算，並且讓小卡可以蓋住地圖：
> §12.8 那條「不能蓋住士兵」管的是常駐 UI，不是讀完就關的清單卡片。

### 版面

地圖滿版鋪底，HUD 與控制列半透明浮在上面，控制列容器 `pointer-events: none`，
按鈕之間的空隙點得到底下的地圖。

```
[◎] [走] [誌]  ← 右上工具列。◎ 只在鏡頭被拖離時出現
               誌 面板頂端就是戰況帳目

[ 待機 ]                              ← 獨立在方向盤上方，間距 >= 一個按鈕高
                                        （這一區唯一不可逆的動作）
[    ] [ ↑ ] [蹲立]     [    ] [模式]  ← 兩邊都是左上角留空
[ ← ] [ ↓ ] [ → ]      [ 包 ] [ 用 ]  ← 背包／使用準備欄的東西
                       [ 彈 ] [ 換 ]
```

不可用的按鈕**灰掉而非隱藏**——按鈕消失會導致其他按鈕位移，位移會破壞肌肉記憶並造成誤觸。

觸控命中區 ≥ 48×48 CSS px **且互不重疊**，320px 寬視窗實測通過（`scripts/a11y.mjs`）。

**鏡頭夾制的邊界是「可觸區域」而不是視窗。** HUD 與控制列浮在地圖上，若照視窗邊界夾制，
士兵走到地圖下緣時會被壓到控制列底下——而 v0.3 把開火鍵拿掉之後，射擊與互動全靠點地圖，
被蓋住就等於完全不能操作。所以垂直方向夾在 HUD 底部與控制列頂部之間。
`camera.test.ts` 會驗士兵在地圖九個位置（四角、四邊中點、正中）時，
自己與四個正交鄰格都完整落在可觸區域內；`a11y.mjs` 再在真實瀏覽器上量一次視覺遮擋。

### 鏡頭可以拖了（v0.8）

交戰以射擊為主，敵人卻常常因為射程關係落在畫面外。所以地圖現在可以拖曳平移，
位移超過 **10 CSS px** 才算拖曳、否則算點擊——這個門檻不是可選的：
就算關掉點擊移動，地圖點擊仍有鎖定、屍體、互動等功能，沒有門檻就會把拖曳誤判成點擊。

鏡頭偏離時右上出現置中鍵；**玩家做任何動作後鏡頭自動置中**回士兵。

**演出視線內的敵人動作時，鏡頭強制帶到該行動單位，並取消手動平移。**
若不做這件事，玩家拖到別處觀看時，v0.6 花一整版建立的逐一演出等於沒有播——
自由鏡頭不可以悄悄把回饋可讀性吃掉。拖曳只在玩家自己決策的期間有效。

### 點擊地圖移動可以關掉（v0.8）

右上的「走」鍵。預設開啟，關掉之後點地圖仍可鎖定敵人、看屍體、與相鄰目標物互動、
看自己的狀態——**只有「點空格尋路移動」被停用**。

> 這條稽核本身踩過兩次坑，都記在腳本裡：
> 一是按鈕縮小後用 `::after` 外擴命中區，結果相鄰按鈕的外擴區互相重疊、搶走對方的角落；
> 二是改用 `elementFromPoint` 測四角時，忘了 `border-radius` 會裁掉圓角的命中區，
> 導致 52px 的圓角按鈕被誤判成過小。現在量的是「矩形尺寸 + 兩兩不重疊」，
> 正是規格 §12.1 要求的兩件事。

## 對規格的補充與判斷（請 review）

**資料模型的增補**（規格 §4 已同步）

`Unit` 增加 `name`（UI 顯示）、`nextActAt` / `moveTime` / `transitionTime` / `transitioning`
與 `pendingSequence`（排程器與系列動作）；`facing` 從 v0.8 起是**規則欄位**而非美術欄位；
`RawMap.enemies[]` 增加選用的 `facing`（初始面向，預設南）；
`GameState` 增加 `clock`、`rng`、`deployed`、`pendingReinforcement`、`nextEntitySerial`、`log`；
`Objective` 增加 `pos`；`MapData.tiles` 是扁平的 `TileType[]`。

**v0.12 的判斷**

1. **基準移動速度從 10 變成 12**（見上）。這不是我選的，是「封合劑重 5 + 初始帶 1 個 +
   不調既有數值」三條同時成立的結果。我照規格實作、量出影響、寫在這裡，沒有自己補償。

2. **右下動作區改成兩欄三列。** 五顆排一直行會吃掉 292px，可觸區域只剩 180px，
   地圖直向只看得到五格半（v0.11 是七格半）。兩欄三列是 172px，把一百多像素還給地圖。
   左上角留空，與左下移動區同一個慣例。

3. **背包與日誌做成滿版面板，連按鈕群一起蓋掉。** 打開它們的當下你在讀清單而不是在打，
   看得完整比看得到底下的地圖重要。退出只靠「關閉」。

4. **二次確認用「同一顆鍵按兩次」而不是對話框。** 手機上單手可達，
   而且不會把已經滿版的背包再蓋一層。

5. **自動機器人學會用封合劑**（血過半 + 沒人瞄得到才用；被瞄準時放棄須重來的序列）。
   不教它的話基準數據只有封合劑的重量代價、沒有它的好處，那個對照沒有意義。

**v0.11 的判斷**

1. **新增一項「不移除敵人也走得到」的驗證**（變更單沒列）。一格寬的走廊裡一隻敵人就是一道牆，
   mission_02 初版被自己的守衛塞死了。這條同時也是 §1.1「路線分歧多」的可檢查版本。

2. **「必經暴露」與「最短路徑暴露」分成兩個數字。** 規格的措辭是「必經」，
   而最短路徑上的暴露不算必經——玩家可以繞。所以驗證用二分搜尋 + 受限 BFS 算真正的必經值。

3. **加了「方向性掩蔽覆蓋率」統計**（變更單沒列）。這是 v0.10 卡住的那個數字，
   不量出來就沒辦法判斷一張圖對 `targetExposure` 友不友善。

4. **三支瀏覽器腳本釘死 `?map=mission_01`。** 它們的座標全部是那張圖的，
   測的是介面與流程而不是地圖，隨機選圖會讓它們無意義地變紅。

**v0.10 的判斷**

1. **開火的宣告在執行時會重新瞄準。** 變更單說失效條件是「脫離視線、脫離射程、已死亡」，
   我一開始實作成「目標必須待在同一格」，結果笨機器人每個動作都在走，敵人一槍都打不出來。
   照字面的三個條件才對：玩家要真的破壞射線或拉開距離才吃得掉那一發。

2. **射手蹲下多了一個條件：蹲下之後仍要看得見目標。** §3 的字面是「有掩蔽且對玩家有視線時蹲下」，
   但緊鄰半身掩體蹲下是雙向阻擋（v0.8 §7.2），所以照字面做會讓射手把自己弄瞎、
   然後在「蹲下→失去目標→站起來」之間來回。以蹲下**之後**的視線為準才是那句話的意思。

3. **「打得到就打」與「換位」的比較只用位置項，不含 approach。** 含了會震盪：
   approach 對相鄰兩格符號相反，A 想去 B、到了 B 又想回 A。

4. **口令加了顯示上限**（一個單位只留最新一句、全畫面最多五張）。
   看不見的敵人是瞬間結算的（§12.12 不給延遲），一整批口令會在同一幀落地，
   不設上限會沿著方位排成一道字牆。

**v0.9 的判斷**

1. **`Corpse` 改名為 `LootPile` 並加上 `kind`。** §4.1 的三種來源共用同一套兩段式文法與同一個面板，
   分成三個型別的話面板要寫三份、拾取指令要開三條路。`state.corpses` 因此變成 `state.loot`。

2. **`TAKE_ALL` 在一件都拿不動時改為非法**（變更單沒提）。難度探針因此卡死：
   背包滿了還一直按，每按一次白花 10 時間卻什麼都沒拿到。這是規則漏洞不是機器人的錯。

3. **HUD 的「遺留」只算己方遺體**，不算沒開過的補給箱——那不是損失，只是還沒去拿。
   結算的第二份清單則照 §6 列出所有還在戰場上的東西，兩者問的問題不一樣。

4. **結算標題要分得出撤離與止損**（§5.3 明說是兩件事，但兩者的 `result` 都是 `ABORTED`）。
   判準是 `extracted` 有沒有內容。

**v0.8 的判斷**

1. **`explored`（地形記憶）沒有做。** 變更指示 §1.5 要求「已探索地形維持繪製」，
   而本專案的地形**本來就一律照畫**（只有單位受視野限制），所以這條天生成立。
   我一度加了三層迷霧（看得見／記得／沒看過），但那等於替專案引進了它從來沒有的
   戰爭迷霧——那是玩法改動，不在這次範圍內，已經收回。

2. **敵人被噪音吵醒時不轉向。** §1.2 只列了三條面向規則（移動／ALERT／IDLE），
   噪音不在其中，所以照字面實作：它會在開始朝噪音走的時候才轉過去。
   若試玩覺得「背後被開槍還傻站著面向前方」很怪，在 `emitNoise()` 加一行 `faceToward` 即可。

**行為上的判斷**

1. **`ADVANCE` 指令**：行動權不在玩家手上時，一個動作一個 Command。UI 用計時器逐步送出，
   玩家看得到「誰往哪裡走了」——否則「衝鋒型比你快」在畫面上不成立。
   看不見的敵人動作會自動快轉，不讓玩家乾等。（v0.6 叫 `ENEMY_STEP`；v0.7 沒有敵人回合了。）

2. **鎖定不放進 `GameState`**：它純粹是介面狀態，不影響規則。放進去只會污染規則層的純粹性。

3. **AI 追擊的目標格允許被佔據**：搜索時的 `lastKnownTarget` 往往就是玩家現在站的地方；
   若不允許，整條路徑會算不出來、敵人原地發呆。實際「不能走進去」由下一步的佔據檢查擋下。
   這是寫 AI 噪音追擊測試時抓到的 bug。

4. **噪音只喚醒 IDLE**：照規格 §8.3 字面實作。已經在 ALERT / SEARCH 的敵人不會因為新槍聲
   更新 `lastKnownTarget`。若試玩覺得怪，改 `core/combat.ts` 的 `emitNoise()` 一個條件即可。

5. **敵人開火的噪音半徑設為 0**（`data/actors.json`），讓噪音機制純粹是
   「玩家自己的選擇引來了誰」，避免敵人互相喚醒造成雪崩。

6. **`toHitChance` 的 `target` 放寬為 `Unit | null`**：濺射武器日後要能對空地開砲
   （`impactPos` 與目標格分離的意義就在這）。MVP 的 UI 只提供對敵人開火，core 不擋。
   `canAttack()` 也不檢查目標陣營——規格 §8.2 明講不做友軍傷害豁免。

7. **`用`（互動）鍵已刪除**：規格 §12.7 的動作區只列技能／彈／換三顆，
   而互動已經由地圖點擊文法涵蓋（相鄰的終端、補給箱、撤離點）。
   站在目標格上時，點自己的詳細狀態卡片裡也有一顆互動鍵。

8. **HUD 只顯示武器型號**（`AR-9 制式步槍` → `AR-9`），完整名稱在點自己的詳細面板裡。

## 四張地圖：三個對照實驗加一個基準

專案至今所有的數值——掩體密度、射程、視野、空投點間距、負重門檻、AI 權重——
**全部是在同一組幾何上調出來的**。那是一個樣本。

| id | 名稱 | 要驗證的假設 |
|---|---|---|
| `mission_01` | 廢棄水處理廠 | 綜合基準 |
| `mission_02` | 輸送管廊 | **狹窄空間。**正交直線對射是否致命；側翼繞行在窄空間中是否仍可行 |
| `mission_03` | 乾涸沉澱池 | **開闊地。**有安全但繞遠的選項時，玩家會不會選它 |
| `mission_04` | 舊倉儲區 | **掩體密集。**`targetExposure` 繞側翼是否真的會發生 |

完整統計在 [`docs/map-stats.md`](docs/map-stats.md)，由 `npm run map:build` 自動產生。

### mission_04 的掩體是**縱向**的

v0.10 量到「mission_01 上十個敵人有九個身邊沒有任何掩蔽」。原因是方向：
掩蔽只看目標**朝向射手那一側**的鄰格，所以一排水平的半身掩體提供的是對
**南北向**射手的掩蔽——而 mission_01 的動線是東西向。

`mission_04` 改成縱向貨架列，走道是南北向的平行推進路線，掩蔽對東西向的交火生效：

| | 對東西向射手 | 對南北向射手 |
|---|---|---|
| mission_01 | 24% | 51% |
| mission_04 | **45%** | 19% |

這是 v0.10 的 `targetExposure` 第一次有東西可用。

### 為什麼不做程序化生成

本作的整套戰術系統長在地形上：掩蔽等級、正交直線對射、面向盲區、側翼路線、
空投點間距、噪音傳播。**地形不是背景，是規則的一部分。**

更根本的是：**生成器本質上是把「什麼叫好地圖」寫成程式，而那些判準目前還不存在。**
手刻地圖就是發現這些判準的過程；驗證工具會把發現的判準固化成可檢查的條件，
將來直接成為生成器的約束。

### v0.13 給驗證器加的兩條約束

**預估完成路徑時間**——走完所有目標再回撤離點的最短路徑 × 基礎移動時間。
這是靜態的下限估計（實際一定更高），所以進得了 CI，不必跑機器人。
局外層會把任務串起來，一場長度失控只是煩人，一場接一場就是災難。

**方向性掩蔽差距 ≤ 20 個百分點**——掩體列的走向等於在決定
**哪個軸向的交火是安全的**。若主目標在北方，玩家整趟推進都在南北軸上交火，
那張圖對他是 19% 還是 51% 的掩蔽，完全是作者無意間決定的。

這一條逼著我動了 mission_01（24/51，差 27）和 mission_04（45/19，差 26）——
前者加了縱向管線、後者加了橫向棧板，現在是 38/51 和 46/31。

### 地圖驗證工具

`scripts/build_maps.mjs` 同時是產生器與驗證器，納入 CI，**任一張圖不過就變紅**。
門檻全部在 `rules.json → mapRules`。

它抓到的第一個真問題就很有代表性：**一格寬的走廊裡，一隻敵人就是一道牆。**
單位不能互相穿越，所以 mission_02 初版的敵人把唯一路線全部塞死了——
真人可以把它打掉再過，但自動機器人的 `findPath` 直接回傳 null、原地卡到天荒地老。
現在有一項檢查是「**不移除任何敵人也走得到所有目標**」。

另一個值得記的是「暴露長度」有兩個數字：

- **直線**＝走最短路徑要連續暴露幾格
- **必經**＝在所有走法之中最好的那一條，還是得暴露幾格

規格的措辭是「不存在完全無掩體的長距離**必經**路段」，所以檢查的是後者——
能繞開就不算問題。必經那一項是二分搜尋 + 「不允許連續暴露超過 k」的 BFS 算的
（狀態是「格子 + 目前連續暴露長度」）。兩者差距大，代表這張圖給了「繞路換安全」的選擇。
